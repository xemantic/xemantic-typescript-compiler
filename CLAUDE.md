# CLAUDE.md

This file captures only what cannot be inferred from the codebase itself.

## Rules for editing this file

Both developers and AI agents are expected to add entries as they encounter surprises.

- **Add an entry** when you encounter something unexpected: a build quirk, a non-obvious constraint, a dependency gotcha, or any behavior that would surprise the next agent or developer.
- **Add an entry** when a developer flags an anti-pattern produced by AI — describe the anti-pattern and the preferred alternative.
- **Do not** add codebase overviews, directory listings, or anything discoverable by reading the source.
- Keep entries concise: one line per lesson, grouped under a heading if a theme emerges.
- **Durable-invariant test** before adding a gotcha: "Would a future agent rediscover this in under 60 seconds via Grep + reading source?" If yes, it belongs in the git commit message, not here. Every entry costs tokens on every session — the bar for inclusion is **future agents will break things if they don't know this**. Per-fix narratives (test name, specific code path, fix story) go in PLAN-PHASE-4.md session notes instead.
- **Format rule (2026-06-10 trim — this file was audited down from 284 KB to 170 KB; do not regrow it)**: a new entry is 1–3 lines stating the trap/invariant and where to look — NOT the fix story. No B-numbers, round numbers, or test-name narratives in the entry body (the session note carries those); no new per-round `### Round-NNN gotchas` sections — file new entries under the matching topical section. If an entry needs more than ~5 lines, the invariant probably isn't isolated yet — distill it.

## Known gotchas

- **Do NOT poll for a Gradle run with a `while kill -0 $(pgrep -f "GradleWrapperMain.*jvmTest") ...; do sleep N; done` wait-loop — it never exits.** `pgrep -f` matches against the FULL command line, and the wait-loop's OWN command line literally contains the string `GradleWrapperMain.*jvmTest` (inside the pgrep pattern), so it matches ITSELF → `kill -0 <self-pid>` always succeeds → the loop sleeps forever, orphaned (harmless/idle, but never terminates and clutters the process list; clean up with `kill <pids>`). There is no need to poll at all: launch the suite with the Bash tool's `run_in_background: true` and react to the `<task-notification>` that fires when it completes (the harness re-invokes you). If you must poll for something, pick a pattern that cannot match the poller itself (e.g. a marker file's existence). Two long-lived JVMs (the Gradle daemon + `KotlinCompileDaemon`, ~hours uptime) are NORMAL idle build daemons — leave them; they speed up builds and auto-shut-down after their idle timeout.
- `project.exec {}` is not available in Gradle 9 Kotlin DSL task `doLast` blocks — use `ProcessBuilder` directly instead.
- TypeScript compiler tests are **generated** by `./gradlew generateTypeScriptTests` into `build/generated/typescript-tests/`; this task requires the TypeScript repo to be cloned first (done automatically via `cloneTypeScriptRepo` dependency). Never edit generated files manually.
- **Deprecated features skipped in JS emit tests**: Parameterized JS emit tests for `target=ES5`/`ES3` and `module=AMD`/`System`/`UMD` are not generated (deprecated in TypeScript 6.0, removed in 7.0/tsgo). Error baseline tests for these combinations ARE still generated since TS5107/TS5108 deprecation diagnostics must still fire. The `effectiveTarget` maps ES3/ES5 → ES2015 so no downlevel transforms are needed.
- **Disabled test category**: `.errors.txt` error baseline tests are commented out in `build.gradle.kts` `generateTypeScriptTests` task — search for `TODO: Re-enable when type checker is implemented`. Re-enabling adds ~9,055 tests (see PLAN.md item 4c).
- Kotlin 2.x disallows `.` in backtick-quoted JVM method names (error: "Name contains illegal characters: .."); sanitize test function names by replacing dots with underscores (e.g. `foo_ts` not `foo.ts`). Some TypeScript test base names contain dots beyond the extension (e.g. `accessors_spec_section-4.5_error-cases`), so the entire `nameWithoutExtension` must have dots replaced, not just the `.ts`/`.js` suffix.

### Checker walker gotchas

- **Any NEW full-tree expression walker MUST handle `BinaryExpression` iteratively (worklist/right-spine), not recursively** — `binderBinaryExpressionStress` is a deeply-nested `a+b+c+…` chain that StackOverflows a naive `walk(left); walk(right)`, and a crash mid-check ABORTS JS emit, so the regression shows up as a JS-EMIT output diff (NOT in the `find_candidates` EXTRA bucket — only the failing-set diff catches it). B98b's `walkThisTypeExpr` learned this the hard way. Reference iterative patterns: `checkArgCountInExprCore`'s BinaryExpression case (right-spine while-loop) and B98b's worklist (`ArrayDeque` frontier).
- **MappedType walkers must remember to walk `typeParameter.constraint`**: A `MappedType` AST node has FOUR meaningful child positions: `typeParameter.constraint` (the constraint of `[K in C]`, e.g. `keyof T`), `nameType` (after `as`), `type` (the value), and the typeParameter NAME (introduced into a child scope). Tree-walking visitors must hit all four. Crucially the constraint must be walked in the OUTER `scope` (not the mapped child scope) — the TP being introduced is NOT in scope inside its own constraint. Reference patterns: `collectTypeReferenceNames` (Checker.kt:3890) and `checkUnresolvedInType` (Checker.kt:13931) both walk the constraint correctly. Symptom of forgetting: TS2304 / TS2503 / TS6133 for a name only-used inside the constraint silently never fires.

### Scanner/Parser gotchas

- **`parseQualifiedName` emits TS1003 "Identifier expected." (overrideLength 0, at the position right after the dot) for a MISSING right side after `.`** (`import x = A.B.<EOF>`/newline). It previously let `parseIdentifierName` silently produce an empty Identifier with no error. The gate is `!isIdentifier() && !isKeyword()` after a consumed `.`; it `break`s and leaves a zero-width missing `right`.
- **A `TypePredicate`'s `parameterName` is a `TypeReference` wrapping the identifier** (`x is U` → `parameterName = TypeReference(typeName = Identifier("x"))`), NOT a bare `Identifier`. Resolve via `(parameterName as? Identifier) ?: (parameterName as? TypeReference)?.typeName as? Identifier`. Matching only `Identifier` silently returns null (B378's `resolveUserTypeGuardNarrowing` hit this — the narrowing never fired until the TypeReference case was added).
- **Regex grammar diagnostics belong in `emitRegexGrammarSubset` (Checker.kt — the faithful tsc scanRegularExpressionWorker port, annexB=true)** — extend ITS subset rather than adding parallel narrow emitters; an out-of-subset construct must BAIL the whole regex (FN-only, zero FP by construction). Currently bailing: groups `(...)`, the `v` flag, octal escapes, unterminated classes — what `regularExpressionScanning` still needs. tsc compiler sources are readable via `git -C typescript-repo cat-file -p HEAD:src/compiler/scanner.ts` (worker at lines 2613–3609) even though the working tree is fixture-sparse.
- **A literal U+FFFD in token position is the BINARY-FILE marker** (`Scanner.sawBinaryFileMarker`): the rest of the file becomes ONE Unknown token and the parser reports TS1490 at (0,0) AT SCAN TIME inside `nextToken()` — the timing is load-bearing: the same-start dedup must suppress the follow-up TS1128 when the marker starts at offset 0 (corrupted_ts) but keep it elsewhere (TransportStream_ts).
- **Two kinds of empty-name Identifiers exist after parse recovery**: the binding-element property-name recovery synthesizes ZERO-WIDTH missing names (`pos == end`); `parseIdentifier`'s TS1003 fallback returns width ≥ 1. Recovery logic keyed on "missing name" must test `pos == end` — matching the TS1003 kind changes how far speculative lookAheads advance (regressed an alias-type parse before the gate).
- **Zero-width missing declaration names sit at the PREV TOKEN'S END, not the offending token** (`parseDeclarationNameOrMissing`, tsc createMissingNode at getNodePos — `function throw()`'s missing name anchors TS7010/TS2300 at the SPACE after `function`); the TS1359 it reports at the unconsumed keyword same-start-dedups the follow-up '('/'{'-expected. Use this helper for new reserved-word-in-name-position recoveries, not parseIdentifier.

- **A `#`-private class-member name Identifier KEEPS the leading `#` in `.text`, and `.pos` points AT the `#`** — the scanner emits `#name` as one token, despite `parsePropertyName`'s Hash branch suggesting it's stripped. Detect private members via `name.text.startsWith("#")`; `source[name.pos - 1] == '#'` lands on the char BEFORE the `#` and silently matches nothing.
- **Multi-base heritage with a GENERIC base before a comma is MISPARSED (NOT yet fixed)**: in `interface C extends A<string>, A<number>` the non-last generic base parses as a synthetic `ParenthesizedExpression` (instantiation-expression) — its `.typeArguments` are LOST, the node's `.end` overshoots (doubles the trailing `>` in source-substrings), and `resolveBaseSym` returns null for it. Parser fix is risk-bearing (all multi-base extends/implements), deferred. Checker workaround for the same-base TS2320 case: `checkMultiBaseInStatement` extracts each base's `(name, typeArgs)` from SOURCE via bracket-matching — same-base-different-args logic must use that path, NOT `.typeArguments` or the resolved-base property loop.
- **JSX-vs-generic-arrow disambiguation in `.tsx` files**: In `parsePrimaryExpression`'s `LessThan` branch, when `isJsxFile`, peek at `<Identifier extends X...>`. If X is an Identifier / type-keyword / open delimiter / `typeof` → generic arrow, fall through to the existing generic-arrow / type-assertion detection. If X is `/`, `>`, or `=` → JSX (boolean attr shorthand `<T extends/>` or attr=value `<T extends={x}/>`). The broader gate `<Identifier extends` (without checking what follows) regresses `parseJsxExtends2_ts`. Tightened gate fixes both `parseJsxExtends2_ts` (JSX) and `declarationEmitRecursiveConditionalAliasPreserved_ts` (generic arrow).

- **`parseParenthesizedOrArrow` mirrors tsc's tristate worker and the GATE ORDER is load-bearing** (B311/B320): `()`+third-token, `(ident:`-True, `(...`-True, then the tristate-FALSE cut — where a MODIFIER followed by an identifier (`(public x`, `(readonly x`) is True, NOT false — then the `=>`-finding complex lookahead. Detection runs at PRIMARY level (tsc: ASSIGNMENT level), so `(x: T)` as a binary right-operand wrongly arrows — blocks `ambiguousGenericAssertion1`; fixing needs an allowArrow flag threaded from assignment contexts.
- **tsc grammar codes our PARSER emits (TS1248/TS1031/TS1155/TS1183/…, `GRAMMAR_CLASS_CODES` in TypeScriptCompiler.kt) do NOT count as parse diagnostics for the hasParseDiagnostics suppression trigger** — a new grammar-code suppression must use `filesWithRealParseDiagnostics`, never `parser.getDiagnostics().isNotEmpty()`, and must exempt `.js` files (plain-JS grammar errors flow through tsc's separate syntactic walker, no suppression).
- **`=>` TERMINATES a variable-declarator list** (tsc isVariableDeclaratorListTerminator error-recovery tweak): the list loop's silent `break` + parseSemicolon's `=>` trigger together produce tsc's "';' expected." at the `=>` — do not "fix" the break into a ',' expected report.
- **A zero-width MISSING Block (pos == end, no statements) is the "aborted signature" body convention (B324/B325) and its consumers deliberately DISAGREE**: TS7010 + the TS2391 PAIR-gap rule treat it as bodyless (tsc nodeIsPresent), the TS2391 FINAL missing-impl rule treats it as a body (tsc `!node.body` — "unifying" these breaks reservedWords3), the emitter prints `function f() { }`, and a `=>`-followed recovery keeps a NULL body instead (tsc erases those from emit — dottedModuleName).
- **`lookAhead` vs `tryScan`**: `lookAhead` ALWAYS restores scanner state. `tryScan` keeps scanner state if callback returns truthy. Use `lookAhead` for probe-and-decide patterns; use `tryScan` for "try to parse, keep results if success."
- **A *parenthesized* function/ctor type is `ParenthesizedType(FunctionType)`, NOT a bare `FunctionType`/`ConstructorType`** (fallback in `parseFunctionOrParenthesizedType`) — union/intersection-member grammar checks (TS1385–1388) can just test `member is FunctionType || member is ConstructorType`. For TS-matching spans: `scanner.getPrevTokenEnd()` right after `parseOptional(Bar/Ampersand)` = span start (incl. trivia after `|`/`&`); `getPrevTokenEnd()` right after parsing the member = its TRUE end (avoids `node.end` overshoot).
- **`lookAhead` does NOT restore diagnostics**: The parser's `lookAhead` restores scanner position and the `token` field, but any `reportError`/`parseExpected` failures during the callback permanently add to `diagnostics`. When using `lookAhead` with complex parsing (e.g., `parseComputedPropertyName()`), save `diagnostics.size` before and trim after to discard speculative errors.
- **`reScanGreaterToken`** (splitting `>>` to `>` for nested generics) was implemented but caused 4-test net regression — left disabled in the parser. The implementation in `Scanner.kt` is correct; the issue is likely subtle interaction with `tryScan` nesting. Re-enable cautiously.
- **`getPos()` in Parser** = `scanner.getTokenPos()` (start of current token), **`getEnd()`** = `scanner.getPos()` (end of current token text). After `parseExpected()`, the scanner has ALREADY advanced to the next token — so `getPos()` is the start of the NEXT token.
- **TS1007 related info for missing close delimiters**: Use `parseExpectedClosing()` (not `parseExpected`) when closing `)` in statement-level constructs (`if`, `while`, `with`, `do-while`). This provides `!!! related TS1007` pointing back to the opening `(`. DO NOT use this globally (in `parseExpected`) — it causes 59+ FP regressions in error recovery tests because the `openTokenStack` doesn't track delimiter types and pops incorrectly in complex error recovery scenarios. For general `parseExpected(CloseParen/CloseBrace)`, only emit TS1007 at EOF (current behavior).
- **Extending squiggle span to include `;`**: When a parser diagnostic should cover the trailing `;` (e.g. `[]: number;` → entire 14-char span), call `parseSemicolon()` first (consuming `;` if present), then use `scanner.getPrevTokenEnd()` for the span end. `getEnd()` is wrong because it returns the scanner position AFTER the next token is scanned. `scanner.getPrevTokenEnd()` = position right after the last-consumed token's text, before the next token's trivia.

- **`isStartOfType` inside `scanner.lookAhead`**: Parser's cached `token` field is NOT updated inside `scanner.lookAhead`. When checking what token follows, pass `scanner.getToken()` explicitly: `isStartOfType(scanner.getToken())`. Using the parser's `token` field inside lookAhead checks the OLD token (before the lookAhead scan), not the advanced token.

- **`TemplateLiteralType` parsing is SHALLOW — `templateSpans` is ALWAYS empty** (even with `${infer X}`/`${TypeName}` placeholders); the raw source slice lives in `head.rawText` (`skipTemplateType()`). Any checker walker needing the AST inside `${...}` gets nothing — string-scan `head.rawText` instead — and note `head.rawText` INCLUDES the surrounding backticks (strip before regex/display use, B297) (see `extractInferNamesFromRawTemplate`, which covers `${... infer NAME ...}` scoping ONLY; reference-tracking walkers need their own raw-text scan).

### Emitter gotchas

- **Tab preservation in error squiggles**: The error baseline formatter must preserve tab characters from source lines in the squiggle indentation — tabs stay as tabs, other characters become spaces. Don't use `" ".repeat(col)`.
- **Numeric literal property access**: `1.foo` is ambiguous in JS (the `.` is a decimal point). Emit `1..foo` when the numeric literal has no decimal point, exponent, or `0x`/`0b`/`0o` prefix.
- **Yield expression operand parsing**: Use `isStartOfExpression()` check (not `!canParseSemicolon()`) to determine if yield has an operand. `canParseSemicolon()` returns false for `]` and `)` which would cause yield to try parsing them as expressions. TypeScript checks `!hasPrecedingLineBreak() && (asterisk || isStartOfExpression())`.

### Transformer gotchas

- **`ClassTransformResult` has FOUR statement channels (leading / trailing / privateState / members) consumed DIFFERENTLY by three callers** — transformClassDeclaration emits leading+trailing as statements; transformClassExpression's no-statics path (B338) and statics path (B340/B342) fold them into the capture comma list with load-bearing ordering (privateState → computed captures → __setFunctionName → statics). A new state channel wired into only one caller silently drops its statements in the others.
- **tsc assigns generated temp NAMES at PRINT time per scope** — a function-local temp avoids ENCLOSING scopes' generated names (`_r` when the file used `_a.._q`) while SIBLING functions each restart at `_a`. The transform-time `withFreshTempVarCounter` per-function reset reproduces only the sibling case; matching both needs print-time name resolution (parked, staticFieldWithInterfaceContext). PARTIAL infra (B348): top-level destructuring-CHAIN temps allocate as placeholders via `nextChainTempName()` and rename at file end (`renameChainTemps`, base = final tempVarCounter) so file-HOISTED temps (`var _a..;` printed at top) grab the first names; function scopes name immediately — the gate is `tempScopeDepth > 0 || functionScopeDepth > 0` (method bodies bump only the latter; missing it leaks raw placeholders into the emit).
- **Async GENERATORS downlevel below ES2018 while plain async is native from ES2017** — the gate is split (`isAsyncGenerator … < ES2018`, `isAsync … < ES2017`) at THREE sites (fn decl / fn expr / method); keep them in sync. The fn-expression `__asyncGenerator` wrapper Block inherits the SOURCE body's single/multi-line form.
- **ES-decorators (TC39, !experimentalDecorators) dispatch BEFORE the legacy path in transformClassDeclaration**, and the three builders (`transformEsDecoratedClass*` / `buildEsDecoratedClassExprIife`) produce FINAL AST — never re-transform their output. The comma form rides the es2015 field-to-ctor downlevel by rewriting decorated field INITIALIZERS to `__runInitializers(...)` BEFORE transformClassBody; CJS classifies the resulting `let C = (() => …)()` via `esDecoratedClassNames` (keep-declaration + trailing `exports.C = C;`, not Direct-export).
- **Orphaned comments (erased declarations)**: Only preserve a leading comment from an erased declaration if there is a blank line (≥2 newlines) between the comment's `end` position and the declaration's `pos`. Adjacent comments are part of the declaration and are dropped.
- **CommonJS transform ordering**: Applied AFTER all other transforms. `transformToCommonJS` receives already-transformed statements. The `isModuleFile` check uses the ORIGINAL source file statements.
- **`transformToCommonJS` is CJS-only**: returns early for ESM/AMD/UMD/System outputs. Any post-process placed inside it (e.g., decorator-metadata safety wraps) won't fire for those module formats. For across-module-format post-processing, add the code to `transformPhase3`'s tail (after the AMD/UMD/System branches return, just before the final `return sourceFile.copy(statements = ...)`). Symptom of getting this wrong: code compiles clean, test still fails with the same diff, debug println never prints.
- **Constructor prologue ordering**: When inserting parameter-property initializers into an existing constructor body (no `super()` call), insert AFTER prologue directives (`"use strict"`, `"ngInject"`), not at index 0.
- **Type assertion parens**: `(<T>expr)` — the Transformer (not Emitter) must drop them. Fix belongs in Transformer because `TypeAssertionExpression` is already stripped before Emitter sees it.
- **`new (<T>call())` semantics**: `new (A())` ≠ `new A()` — after stripping the type assertion, if the constructor expr becomes a `CallExpression`, it must be re-wrapped in `ParenthesizedExpression`.
- **Static-class-field async arrow defensive capture**: For `class C { static field = async (...) => ... }` under target<ES2022, TypeScript pre-emits `var _a; _a = C;` even when the async arrow body has no `this` reference. The `__awaiter` template is conceptually `this`-binding for static-field-initialized async arrows even when the actual `__awaiter` call passes `void 0`. `staticPropsWithThis` filter in `Transformer.kt` matches this shape via `prop.initializer is ArrowFunction && ModifierFlag.Async in modifiers`. Skip the gate at your peril — removing it regresses `asyncArrowInClassES5_ts`.
- **Non-async arrow expression-body must scope its own hoists**: For `() => obj?.foo` (any arrow whose body is an expression containing temp-var-needing transforms), push a `hoistedVarScopes` entry around body transformation. If any temps were allocated, convert the expression body to `{ var <temps>; return <body>; }`. Without this, optional-chain temp vars hoist to the outer file scope, mismatching TypeScript's emit shape. Async arrows skip this push because `__awaiter` provides its own wrapper.

### Lib-suggestion (TS2550/TS2583/TS2584/TS2585/TS2592) gotchas (round 135, B237–B242)

- **Adding a member to LIB_MIN_TARGET FILTERS it from the interface at unavailable lib levels — which SHIFTS every tuned "and N more" missing-property count involving that interface**: `RegExp.dotAll` regressed `assigningFromObjectToAnythingElse` ("and 11 more"→"10 more"); `Array.flat/flatMap` would shift the Blocker-#4 `genericArrayExtenstions` counts. For members whose PRESENCE is count-load-bearing, use **`LIB_MIN_TARGET_SOFT`**: consulted ONLY by access-site checks (member stays in the interface; property ACCESS still errors TS2550); the property-access-call TS2554 arity check is suppressed for soft-unavailable members. Before adding a HARD entry for a member that EXISTS in the embedded lib, grep the corpus for missing-property displays naming that interface.
- **All LIB_MIN_TARGET gates route through `libFeatureAvailable(intro)`**: empty `@lib` derives availability from `options.target` (harness default target is ES3, matching tsc); explicit `@lib` provides a feature iff some entry's BASE es-version ≥ intro (dotted entries count their prefix level — conservative towards suppression). Do NOT compare `options.target < minTarget` directly in new checks.
- **TS2583 name-availability is split across TWO mechanisms**: the es2015-era FORWARD_DECLARABLE set (`isLibTypeUnavailableEs2015` — Promise/Symbol EXCLUDED there: their TYPES live in lib.es5; their VALUES route through `libProvidesSymbolValue`/`libProvidesPromiseValue` → TS2585 via the TS2693 walker) and `LIB_GLOBAL_INTRODUCING` for later globals (Atomics es2017, AsyncGenerator es2018, BigInt es2020 …) with per-name dotted home-libs. `libUnavailableGlobalSuggestion(name)` is the shared entry; it also SUPPRESSES the TypeReference TS2314 arity check (TS2583 owns the position), and `getReturnTypeOfNewExpression` returns anyType for unavailable callees (else `m.clear()` FPs against the Constructor interface). `Proxy` is deliberately in NO map — tsc's feature map lacks it, so it gets plain TS2304 via a scope.has bypass.
- **`builtinLibDecls` holds top-level statements AND the inner VariableDeclaration nodes**: a `declare var Map: MapConstructor` lib statement binds its SYMBOL's declarations to the inner `VariableDeclaration`, not the statement — `decl !in builtinLibDecls` "user-declared?" identity checks silently mis-fire for lib var globals without the inner nodes (this blocked both Map value-position TS2583 and console TS2584).
- **The TS2550 lib-availability lookup in `checkMemberAccessMissing` is PER-RECEIVER-SHAPE, not just map entries**: string/array/regex-literal receivers, Identifier (a bare lib name resolves to the INSTANCE interface — statics need the `<Name>Constructor.<prop>` fallback key; the embedded lib deliberately has NO ArrayConstructor), NewExpression lib-ctors, CallExpression results, and the namespace Module branch each have their own branch. A new LIB_MIN_TARGET entry won't fire unless the receiver's shape branch exists — when a TS2550 mysteriously doesn't fire, identify the shape and bisect that branch with a marker diagnostic (code 29999).

### Module resolution diagnostic gotchas

- **`typeof import("spec")` parses as `TypeQuery(exprName = ImportType)`, NOT as `ImportType(isTypeOf=true)` (B174)**: the Parser's Typeof branch wraps the ImportType in a TypeQuery and `isTypeOf` stays false. Any checker branch matching "typeof import" type args/annotations must unwrap BOTH shapes (`(t as? ImportType) ?: (t as? TypeQuery)?.exprName as? ImportType`). Symptom of matching only ImportType: the branch silently never fires (the B174 marker-diagnostic trace found this).
- **An explicit `undefined` argument is LEGAL for an OPTIONAL parameter (B176, `allArgumentsMatch`)**: absent and undefined are interchangeable for parameters (exactOptionalPropertyTypes does NOT apply to params). The overload matcher accepts `undefined` args against `questionToken` params; without this, an overload PAIR like `toSpliced(start, deleteCount, ...items)` / `toSpliced(start, deleteCount?)` FP's TS2769 on `f(2, undefined)` against BOTH overloads. If you add per-arg checks to another overload path, mirror the gate.
- **A member declared ONLY `static` does NOT satisfy an instance-side requirement**: statics live in BOTH `members` and `staticMembers` (bifurcation model), so name-presence over-counts — `collectMissingProperties` checks `srcSym.declarations.all { Static in modifiers }`. A bare CLASS identifier in VALUE position is its STATIC side (`typeof B`). The var-decl gate `(!canUse || isAssignable)` is deliberate: the static-aware check must ALSO run when the relation PASSED (the engine wrongly counts statics); relation-failed keeps the standard path (no double-emit).

- **Declaration-emit nameability (TS2883/TS4023/TS2527, `checkDeclarationEmitNameability` + `checkDeclarationEmitComputedSymbolNameability`) is self-contained AST+module-resolution — NO type engine; also runs under the `declarationOnly` checker.** Two load-bearing gates: the TS4023 symbol firewall `computedKeyResolvesToSymbol` (key must resolve to a `Symbol()`-init or `unique symbol` decl — without it enum-member/undefined computed keys FP), and `isValueAccessibleIn` must NOT consult `globals` (Blocker #3 merges all file locals into it, so cross-module symbols wrongly count accessible) — use KNOWN_GLOBALS. A top-level `unique symbol` is accessible via `typeof value`, so only NESTED ones trigger TS2527.
- **`typeof <moduleAlias>` assignability (TS2741, typeofExternalModules family) is a SELF-CONTAINED AST shape (`moduleAliasTypeofShape` + `tryEmitModuleNamespaceTs2741`), deliberately NOT a namespace `Type` in the relation engine** — namespace-as-Type flows too broadly through assignability (rated MEDIUM-risk, rejected). To extend (namespace-import, `export default` module shapes), extend `moduleAliasTypeofShape`, never the relation engine. An `export = X` (module-local class) shape is the STATIC side of X plus a synthetic `prototype` (null pos → no TS2728).
- **TS2349 for CALLING a CJS-default-as-namespace (`cjsDefaultNsShapes` + early branch in `checkSingleCallExpressionTypes`)**: a CJS module's `default` import is the WHOLE `module.exports` namespace (`typeof import("mod")`) — not callable. Two narrowly-gated shapes only: nodenext ESM importer ← `.cts`/`.cjs` with DIRECT `export default`; commonjs+esModuleInterop ← `export =` → require-alias → proper-namespace CHAIN. **DO NOT broaden to all commonjs default-imports** — a direct `export default` under esModuleInterop yields the callable VALUE via `__importDefault` (and `export = fn/class` are callable); the chain requirement is the FP firewall.
- **TS5097 ("import path can only end with '.ts' when allowImportingTsExtensions is enabled") has TWO emission branches in the import-specifier walker (Checker.kt ~23362, B141)**: (1) the original RELATIVE branch (`./foo.ts`); (2) the BARE branch for a `paths`-mapped specifier ending in `.ts`/`.tsx`. The bare branch approximates TS's **resolvedUsingTsExtension** rule with TWO load-bearing checks: the longest-prefix-matching `paths` pattern KEY must NOT itself end in the extension (`"baz/*.ts"` absorbs the `.ts` -> no error), AND a substituted `paths` target must end in `.ts`/`.tsx` AND directly name an existing source file in `fileResults` (use the DIRECT-key forms `t`/`/t`/`./t`, NOT `resolveModuleSpecifier` which does directory-index resolution -- else a package-dir name like `zone.tsx/index.d.ts` matched by `"*":["foo/*"]` wrongly fires TS5097). Both checks are required: dropping the file-resolution gate FP'd `pathMappingBasedModuleResolution_withExtensionInName`; the key-ext check is TS's pattern-absorption rule.

- **TS2694 for `X.Y` inside a `declare module "m"` body where `X` is a MODULE-LOCAL namespace MUST stay AST-based (`checkAmbientModuleLocalNamespaceMemberRefs`)**: the global symbol-merge UNIFIES the module-local and file-level `namespace X` (same name), so a symbol-table lookup wrongly sees the outer block's members and the error never fires. Single-file only — the cross-FILE merged-namespace sibling stays failing (Blocker #3).
- **A `.mts`/`.mjs`/`.d.mts` file is an ES module ONLY under node module kinds (`effectiveModule.isNodeNext`), NOT under commonjs/amd/system/umd** — the rule comes from `impliedNodeFormat`, computed only under node resolution; under amd/system/umd the GLOBAL module setting governs and `export =`/`import = require()` in a `.mts` is LEGAL (an unconditional .mts-is-ESM gate FP'd TS1202 on a 0-errors baseline). MULTI-FILE test options BYPASS `parseCompilerOptions` (built in `parseMultiFileSource`'s own `applyDirective` loop) — any implied-option rule (e.g. `applyImpliedAllowJs`: checkJs⇒allowJs) must be applied at ALL THREE option-finalization sites: single-file parse, multi-file parse, and the driver's post-`optionOverrides` re-apply. - **Debugging "is this checker path reached?": gradle SUPPRESSES test stdout/stderr** (no `testLogging.showStandardStreams` in build.gradle.kts), AND the forked-JVM stderr does NOT land in the test XML's `<system-err>`. Also note: the Checker `init` gates most checks behind `if (!declarationOnly)`; `@emitDeclarationOnly` multi-file runs a `declarationOnly=true` checker that skips them.

Do NOT broaden the script-only walker to module files — it FPs on legitimate module augmentations; extend the augmentation walker with gated branches instead.
- **A BARE (non-relative) ambient `declare module "X"` is a STANDALONE ambient module, NOT an augmentation of a sibling SOURCE file whose basename happens to be `X` (B387)**: `collectModuleAugmentations` merges augmented exports into the resolved target file's locals, but that merge must be SKIPPED when the specifier is bare AND the target resolves to a plain `.ts`/`.tsx` source (not `.d.ts`, not `node_modules`) — tsc only augments `.d.ts`/package ambient modules via a bare name, never a relatively-resolvable source. Relative augmentations (`declare module "./foo"`) DO augment their `.ts` target — gate on the specifier being non-relative, not just the target file type.
- **`resolveModuleSpecifier` does NOT resolve the `.`/`./` package-index specifier** (it returns null) — `import '.'` / `declare module '.'` mean "this directory's index". Any check needing that target must resolve it itself (cf. `resolveAugmentationTargetFile`, B412: sibling `index.{ts,tsx,d.ts}` in the importing file's directory). FP-safe (a re-exported name + a non-mergeable aug decl is always a duplicate). NOT yet handled: which Row2 wins for TYPE RESOLUTION when both an augmentation `type Row2={a}` and a re-exported `interface Row2{b}` exist (tsc uses the first-declared `{a}`; we resolve to the re-exported `{b}` → wrong TS2741 property — cross-file merge ORDER, `mergeSymbolReexportInterface`).
Augmentation vs definition of `declare module "X"` is distinguished by ABSENCE of an inner `export =` (the definition carries it), NOT by `isModuleFile`. Map keys preserve leading `/` (absolute paths) and use `""` for the implicit root.

Match `lastIndexOf("node_modules/")` NOT `"/node_modules/"` — fixtures mix leading-slash conventions and the no-slash form must still match.

### Cross-file infrastructure gotchas

- **`node_modules/*.d.ts` files ARE parsed + bound + in `binderResults`, and their diagnostics DO reach the output** (despite a driver code comment saying node_modules files are "third-party and never reported on" — that comment is about EMIT, not diagnostics; `parsedSourceFiles[fileName]` is set BEFORE the emit-skipping `continue`). Confirmed by the passing `augmentExportEquals7` (reports a node_modules TS2649) and used by B443's `checkGlobalNamespaceMemberConflicts`. So a cross-file checker walk CAN emit diagnostics at node_modules positions — don't assume they're filtered.
- **A cross-file `declare global { namespace NS { … } }` merge is NOT modeled by the binder's symbol tables** — detecting a member-name CONFLICT across files in such a namespace (e.g. `type VNode` in one file vs `export import VNode` in another → TS2300) needs an AST-based dedicated cross-file walker (`checkGlobalNamespaceMemberConflicts`, B443), like the other cross-file conflict walkers. FP firewall: ≥2 DISTINCT files AND a type-alias in the mix (type-aliases are the only kind that can never merge).
- **A cross-file global `type N` (script file) + `namespace N` (DIFFERENT script file) is TS2649, NOT TS2300 (B449, `checkCrossFileTypeAliasNamespaceConflict`)** — tsc routes this degenerate global merge through the module-augmentation path: "Cannot augment module 'N' with value exports because it resolves to a non-module entity." at the type-alias name (the type alias is the "non-module entity"). AST-based (binder doesn't model the cross-file global merge). FP firewall is the SCRIPT-file gate (`!isModuleFile`): the only other corpus file with `type X`+`namespace X` is `reexportNameAliasedAndHoisted`, whose files are MODULE files (module-scoped → no global conflict, excluded). Cross-FILE only (same-file is TS2300, owned by the dup-identifier pipeline).
- **Function-call arity (TS2554) is cross-file via an OVERLAY, not per-file (B434, `checkArgumentCounts`)**: a per-file `funcParams` map only sees the current file's functions, so a SCRIPT-mode cross-file call (`f()` in B where `function f` is in A) was never arity-checked. A program-wide `crossFileFuncs` overlay (top-level FunctionDeclarations from all NON-module non-.d.ts files) is merged as a FALLBACK for NON-module files. Load-bearing FP firewall: merge ONLY for callees absent from BOTH the file's own funcParams AND its binder `locals` (a local binding of any kind shadows a cross-file function — without this guard a local non-function `f` + `f(1)` FPs); cross-file DUP names (same name declared in ≥2 files) are dropped (conservative). TS6210/TS6211 related-info must resolve against the DECLARING file (`FuncParamInfo.declFileName/declSource` → `emitTS2554TooFew(relSource, relFileName)`), else the param position is computed against the CALLER's source (wrong file+offset). Companion: JS-param optionality is JSDoc-aware — `paramInfo(params, isJsFile, jsDocRequiredParamNames(comments))`; a JS param is optional UNLESS a non-bracket `@param name` tag documents it (`@param [name]` stays optional).
- **`mergeSymbolTable` mutates the existing target symbol's `declarations` list**: When `target[name]` already exists, the helper does `existing.flags |= symbol.flags; existing.declarations.addAll(symbol.declarations)` — so calling it twice across the same `result.locals` corpus duplicates declarations on the SHARED symbol object. The init-block merge into `globals` already does this once for every cross-file same-name pair; any additional pass building per-file scope tables MUST NOT re-merge across binderResults via this helper. Use direct `map[name] = sym` assignment with first-write-wins for shared pools and last-write-wins for own-file overrides — no `addAll`, no symbol mutation. Failure mode is silent until a downstream check (e.g. TS6133 unused-T-param, declaration count) sees the duplicated declaration list and behaves incorrectly.
- **`isValueExport`/`isTypeOnlyExportName` cross-file lookups must NOT rely on symbol flags**: `mergeSymbolTable` pollutes the target file's `locals["X"]` symbol with flags merged in from importing files (e.g., `import { T } from "./type"; const T = 0` in file A causes /type.ts's T symbol to acquire BlockScopedVariable|Alias|ExportValue flags). Code that asks "is X exported from file Y as a value or type?" MUST scan `targetResult.sourceFile.statements` directly for declarations of X, not consult `targetResult.locals[X].flags`. Mirror pattern in `isValueExport` (Checker.kt:955) walks the AST and classifies each declaration's kind. Fall back to flag-based logic only when no direct declaration is found (ambient/re-export cases).

### Binder gotchas

- **`canMerge` must include Variable+Module**: `declare const b: T; declare namespace b {}` is valid TypeScript. The binder's `canMerge` must allow `Variable + Module` and `Module + Variable` merging, otherwise the second declaration silently overwrites the first symbol. This matters for `isTypeOnlyImportRequire` which then sees only the namespace and incorrectly elides the `require()`. **BUT (B98.r46): var+namespace merge is allowed ONLY when the namespace is VALUE-FREE (uninstantiated — only types/interfaces).** An INSTANTIATED namespace (one with value exports, e.g. `export var x`) is a SECOND VALUE binding → TS2300 even for `declare var` (`declare var console; namespace console { export var x }` conflicts). The `namespaceVarAllowed` gate (Checker.kt:~19710, duplicate-declaration TS2300/TS2451 path) is `group.filter{namespace}.all{ !isNamespaceInstantiated(it) }` — do NOT re-add a `|| allVarsDeclare` blanket allowance (the old comment "a declare var can merge with any namespace" was wrong; the empty-namespace `b{}` case survives because it's not instantiated).
- **`canMerge` must include Variable+Interface**: `interface Symbol {}` + `declare var Symbol: SymbolConstructor;` is the standard wrapper-type pattern in lib.d.ts. Without this merge, the var silently overwrites the interface — `Symbol` resolves to anyType in type position and `sym = Sym` skips type checking. Same gap blocks any user `class B extends A` where A is `interface A {}` + `declare var A: { new(): A }` (e.g. `staticMismatchBecauseOfPrototype`). Note: enabling this merge also makes lib types like `Object`/`Promise` resolve to real Type.Interface (was anyType), exposing two latent gaps in the relation engine — see `propertiesRelatedTo` OBJECT_PROTOTYPE_PROPERTIES filter and async return-type Promise unwrapping below.
- **Ambient module symbol overwritten by import alias**: `import x = require("X")` in the same file as `declare module "X"` creates an Alias symbol that overwrites the NamespaceModule in `locals["X"]` (Alias doesn't canMerge with Module). `isAmbientModuleTypeOnly` must analyze the ModuleBlock AST directly instead of looking up `locals[name]`.
- **Module augmentation vs definition**: `declare module "X"` in a module file (has imports/exports) is an augmentation. In a script file, it's a definition. `isAmbientModuleTypeOnly` must skip module files to avoid treating augmentations (which only add types) as the full module definition.
- **A `namespace`/`module` symbol does NOT carry bare `SymbolFlags.Module` — it carries `NamespaceModule` (uninstantiated) or `ValueModule` (has value members)**: a check that gates "is this a namespace?" on `flags.hasAny(SymbolFlags.Module)` SILENTLY returns false for most real namespaces (e.g. one with a `class`/`var` member is `ValueModule`). Use `hasAny(SymbolFlags.Module or SymbolFlags.NamespaceModule or SymbolFlags.ValueModule)` (cf. Checker.kt:71904/77421/4755). Symptom: a new namespace-detection walker fires for NOTHING (B393's first run was net-zero because of exactly this).
- **`SymbolFlags.ConstEnum` is set on namespaces holding only const enums**: `bindModuleDeclaration` sets `SymbolFlags.ConstEnum or NamespaceModule` when `ModuleInstanceState.ConstEnumOnly`. Cascades up: `namespace A { namespace B { namespace C { const enum E {...} } } }` makes A, B, C all carry `SymbolFlags.ConstEnum`. So `flags.hasAny(SymbolFlags.Enum)` (= ConstEnum or RegularEnum) returns TRUE for these namespaces. Any code that distinguishes "real enum" from "namespace" must check `declarations.any { it is EnumDeclaration }` rather than relying on the flag alone.
- **Block-scoped declarations are NOT bound** (B83.5, 2026-05-27): `Binder.kt:bindStatement` only dispatches symbol-declaration cases via explicit `when` arms (Variable/Function/Class/Interface/TypeAlias/Enum/Module/Import/Export). The catch-all `else` branch silently ignores `WhileStatement`/`Block`/`IfStatement`/`ForStatement`/`TryStatement`/`SwitchStatement` and every other non-declaration statement, so any `class X` / `interface I` / `type T` / `enum E` / `function F` declared INSIDE their bodies is NEVER bound to file `locals` or `globals`. Consequence: any checker walker that looks up such a declaration by name via `globals[name]` / `result.locals[name]` / `perFileScope[file]?.get(name)` returns null. Symptom: TS2339/TS2551/TS2693/TS2304 silently never fires inside block-scoped class bodies because `classType = null`. Surgical fix pattern when the AST is in-hand: synthesize a transient `Symbol(SymbolFlags.Class, stmt.name.text)` with `declarations = [stmt]` and pass to `getDeclaredTypeOfSymbol(symbol)`. The synthetic symbol must NOT be published to binder tables (`globals.put` / `result.locals.put`) — it's a checker-pass-local temporary; cross-decl merging or multi-pass identity is the binder's job. Used in `checkPropertyAccessInStatement`'s ClassDeclaration branch (Checker.kt:~61539); extend to similar `globals[stmt.name.text]`-based lookups if more shapes surface (other checker walkers that recurse into block bodies but resolve nested decls by name).
- **block-NESTED let/const redeclaration (TS2451) is owned by the dedicated additive walker `checkBlockScopedRedeclarations`, NOT the binder duplicate pipeline** (the binder doesn't bind block-scoped decls, above). It processes Block/switch/try/catch/finally scopes ONLY — function/method BODIES are already covered by an existing function-scope emitter, so processing them again DOUBLE-emits (the tell: a fn-body `let x; let x` reports TS2451 twice); recurse INTO function bodies for their nested blocks but don't treat the body itself as a scope. File/module top-level stays with the binder pipeline.
- **TS2451-vs-TS2300 for a let/const + var collision is decided by the FIRST declaration's kind** (duplicate pipeline `useTs2451`, Checker.kt ~28605): a block-scoped (let/const) declared FIRST → TS2451; a `var` declared first → TS2300. A `function` declaration anywhere in the SAME scope as the let also forces TS2300 (so let+var → TS2451 but let+var+function → TS2300). var-hoisting (a var/function in a NESTED block hoisting into the let's function/namespace scope → TS2451) is NOT yet modeled.

### Type system gotchas

- **Index-signature assignability is asymmetric source-vs-target (B418b)**: a SOURCE index signature does NOT satisfy a TARGET's required NAMED property — `propertiesRelatedTo` must NOT shortcut `sourceProp==null && source.stringIndexInfo!=null` to "present" (`{[k:string]:any}` is NOT assignable to `{one:number}` → TS2741, same as the number-index source). Conversely a PRIMITIVE source vs an ANONYMOUS index-sig-only target relates via the source's APPARENT type: `string`→`{[n:number]:any}` PASSES (String has a numeric index sig) but `string`→`{[s:string]:any}` and `boolean`→`{[n:number]:any}` FAIL — the `structuredTypeRelatedTo` branch must check the apparent type HAS each index sig the target needs (string-index source also covers a numeric-index target). Delegating to `checkTypeRelatedTo(apparent, target)` OVERSHOOTS — `objectTypeRelatedTo`'s index-sig check does NOT enforce source index-sig PRESENCE when the target value type is `any`.
- **`Parameters`/`ReturnType`/`ConstructorParameters` are now MATERIALIZED (B407, `materializeSignatureUtility`, symbol==null dispatch in `getTypeFromTypeReference`)** — `Parameters<F>`/`ConstructorParameters<F>` resolve to a real TUPLE of the sig's param types, `ReturnType<F>` to the return type (not errorType anymore). Additive: returns null (→errorType) for rest/optional params or no matching sig. The TS2344 "does not satisfy `(...args: any) => any`" for `Parameters<typeof Class>` (constructor type, no call sig) is a SEPARATE check (`checkUtilitySignatureConstraint`) gated on the whole ref resolving to errorType.
- **Array-literal→tuple element checking (TS2322) is VAR-DECL-only (`checkArrayLiteralElementsAgainstTuple`, B407)** — the relation engine still SKIPS array→tuple (Checker.kt ~64488 "needs contextual typing, not yet implemented"); the var-decl path now handles the array-LITERAL case element-wise. To cover call-arg/assignment tuple targets, extend that walker (do NOT un-skip the relation engine — array-VARIABLE→tuple is a different, intentionally-conservative path).
- **NameScope carries type-param CONSTRAINTS (`typeParamConstraintOf`, B406)** — populated at `addTypeParam(name, constraint)` sites; a new `addTypeParam` call should pass `it.constraint` if available. Used to detect e.g. `T extends string[]` for the indexed-access TS2536 check. An invalid string-literal index in an indexed-access TYPE (`string[]["0.0"]`→TS2339, `T["0.0"]`→TS2536) fires ONLY for a numeric-LOOKING-but-non-canonical key (`isNumericLiteralName`: canonical iff `String(Number(s))===s`) on an array-shaped object — never a valid array member/index, so FP-safe.

Conditional-type `infer` is AST-guided POSITIONAL unification (`tryEvaluateConditionalWithInfer`), not type-level — `getTypeFromTypeNode` yields errorType for infer-bearing extends-types. FP firewall (load-bearing): ONLY the positive-unification path returns non-null; union-checkType / different-target / arity / non-infer mismatches all return null so the caller falls back to the prior anyType behavior. Bindings layer onto `currentTypeAliasArgs` (a non-null map bypasses the nodeTypes cache → fresh resolution). Tuple/array/fn-type infer positions and union distribution are NOT handled.
TypeScript UNFOLDS a type-alias that resolves to a PRIMITIVE in error displays (`type N = number; let x: N = "s"` shows 'number', not 'N'); object/interface aliases keep their name. Use `displayTargetAnnotation` — currently wired only at the general var-decl TS2322 site; route any other site through it when it shows an alias name where tsc shows the primitive.
`formatPropertyDisplayName` preserves the SOURCE quote char of a non-identifier string-literal property name (via `nameNode.singleQuote`) — do NOT hardcode one quote style; baselines require both single- and double-quoted renders. Numeric-literal names (`{ 0: 1 }`) are NumericLiteralNode → rendered unquoted.

- **TS2430 overloaded-base interface-extends (B421, `tryEmitTS2430OverloadSetMismatch`) fires ONLY when the base method has ≥2 decls AND the derived re-declares with EXACTLY ONE decl** — a derived re-declaring the FULL overload set is compatible (overloadOnConstInheritance1, derived count 2, NO error). - **TS2416 method return type inference**: For methods with body but no return type annotation, default to `void` only if the body has no `return expr` statements. - **TS2610/TS2611 accessor↔property override mismatch (B98.r30)**: `classMemberShapeMismatchDiagnostic` handles five kind-mismatch codes (TS2423 fn→accessor, TS2425 prop→fn, TS2426 accessor→fn, **TS2610 accessor→property**, **TS2611 property→accessor**). - **`signatureRelatedTo` parameter count**: Must check `source.minArgumentCount > target.parameters.size` — if the source function requires more args than the target provides, they're incompatible. Without this, `(a, b) => void` would be incorrectly assignable to `() => any`.
- **OBJECT_PROTOTYPE_PROPERTIES filter**: Names: `toString`, `toLocaleString`, `valueOf`, `constructor`, `hasOwnProperty`, `isPrototypeOf`, `propertyIsEnumerable`. Those broad changes were deliberately avoided; the narrow emission captures the rule for this shape with a tiny FP-surface. The general (A)/(B) fix remains documented in PLAN-PHASE-4.md B87.1c for any future async-generic test the narrow gate misses.
- **The missing-property SUBSET of named→named comparison is SAFE to open (B87.4, round 73)** — `canUseTypeEngine` gates OFF full named→named (class/interface) structural comparison because of the documented 39+ recursive-type-expansion regressions. - **Dotted-only `@lib` (no full es-version base) → `libProvidesBaseValues()` false**: emits the FIXED file-less TS2318 set {Boolean, CallableFunction, IArguments, NewableFunction, Number, Object} and injects `Array` into `typeOnlyNames` (value use → TS2693). - **`formatTypeForDisplay` does NOT render the `readonly` TypeOperator (B87.2, round 73)**: `formatTypeForDisplay(TypeOperator(ReadonlyKeyword, TupleType))` returns `null`, so any diagnostic display for a `readonly [...]` / `readonly T[]` annotation must build it manually as `"readonly " + formatTypeForDisplay(operator.type)`. - **AsExpression (`expr as T`) is visited by `walkTypeAssertionsInExpr` but NOT forwarded to the `onAssertion` callback (B87.2, round 73)**: the shared walker recurses into `AsExpression.expression` but only calls `onAssertion` for `TypeAssertionExpression` (`<T>expr`). - **Protected-member READ access (TS2445/TS2446, `checkProtectedMemberReadAccess`, B446) is a DEDICATED AST pass, separate from B377 (protected WRITES from free functions).** Enclosing class for protected access = the lexical class, or a `this: T` param's class / its constraint's class (null for a free fn with an unconstrained/non-class `this`). TS2445 when enclosing is null or doesn't derive from the declaring class; TS2446 when it derives but the receiver's class isn't enclosing-or-derived. Receiver resolved AST-only (this / param / local-typed-as-class / `new C()` / `this.classProp`); statics, generic-instantiated receivers, `super`, and writes are excluded (writes owned by B377). It does NOT cover top-level reads, static-side reads (`C.staticProtected`), write-context TS2446, or the protected-MISMATCH-in-assignability TS2322/TS2415 chains — `protectedMembers` needs all of those (4 coupled pieces, deferred).
- **`Type.Reference` interning**: Construction goes through `getOrInternReference(target, args)` (CheckerState `referenceCache` keyed on `target.id|arg1.id,arg2.id,...`). Identical instantiations share an instance and `Type.id`, which is what the id-based cycle detection in `relationComparisonStack` relies on. Do NOT call `Type.Reference(...)` directly in new code.
- **`isDeeplyNested` heuristic on parallel target stacks**: `relationSourceTargets`/`relationTargetTargets` track `target.id` of every `Type.Reference` source/target on the active comparison stack. When the same target appears 5+ times on its stack, `checkTypeRelatedTo` short-circuits to `true` (cycle break). Catches infinitely-expanding generic comparisons like `A<T> { x: A<()=>T> }` vs `B<T> { x: B<()=>T> }` whose Refs grow unboundedly and never re-occur identically. The same-target arg-shortcut (step a) ALSO defers to structural on re-entry (`countOccurrences > 1`) so the inner cycle-break can fire instead of an eager arg-mismatch `false`.
- **TypeParam vs TypeParam relates via apparent types**: `structuredTypeRelatedTo` returns `true` when both sides are `Type.TypeParam` and either is unconstrained (apparent type `{}`); when both have constraints, recursively compares those. Without this, generic-method signature comparison treats source's `K` and target's `K` (separate fresh params from `resolveGenericPropertyType`) as opaque-and-distinct → spurious TS2322.
- **`getPropertyTypeForRelation` is depth-bounded** (`relationDepth < 4`): Above depth 4 it falls back to raw `getTypeOfSymbol` because `resolveGenericPropertyType`'s MethodDeclaration branch mints a fresh `Type.Object` + `Signature` + parameter `Symbol`s per call, OOMing in deep overload-permutation comparisons before the deeply-nested heuristic can bail. The `resolvedPropertyTypes` cache (keyed on packed `(ref.id, propSym.id)`) helps for repeated identical queries but each recursion level mints a NEW outer `Type.Reference` (different `ref.id` → cache miss). Don't loosen the cap without a different allocation strategy (e.g. reusing TypeParam declarations instead of minting fresh ones).
- **`instantiateType` walks anonymous property-bag `Type.Object` ONLY (no symbol, no call/construct sigs); it NEVER walks `callSignatures`/`constructSignatures`** — a function-shaped `Type.Object` (function-typed property or method param on a generic interface) keeps its inner sig's outer-TP references un-substituted, and the failure mode is SILENT (per-property elaboration / TS2345-via-constraint just don't fire). Route such cases through `substituteOuterTypeArgsInGenericFnObject` (in-place mutation; safe because `getTypeFromTypeNode` is uncached under `currentTypeParamScope`), as `resolveGenericPropertyType`'s PropertyDeclaration and MethodDeclaration param branches already do — apply the same fix at any new site with this shape.
- **`currentLocalTypes` is first-decl-wins for annotated `VariableDeclaration`**: when multiple declarations of the same name share an annotation (e.g. `var x: T` + `declare var x: T` in a script file), the FIRST resolved type stays. Each `getTypeFromTypeNode(TypeLiteral)` call produces a FRESH `Type.Object` with FRESH member Symbols, so the SAME `{...}` literal at two source positions produces two distinct member Symbols with distinct declaration positions. Without first-wins, `getTypeOfIdentifier(x)` returns whichever annotation was processed last, and TS6500 / TS2728 "declared here" hints point to the wrong source position. Matches Binder's `valueDeclaration` semantics (only set when `existing.valueDeclaration == null`).

- **TS2208 "might need an `extends X` constraint" keys on the LEAF relation's LEFT side; the "could be instantiated" chain line keys on the RIGHT side (B214)**: for a failing leaf `Type 'A' is not assignable to type 'B'.`, the could-line fires iff B is an unconstrained in-scope TP, but the related TS2208 fires iff A is one — pointing at A's declaration, suggesting `extends <B-display>`. They are INDEPENDENT (test1/3 of typeParameterArgumentEquivalence have TS2208 with NO could-line; the reverse direction has the could-line with no TS2208 when A is a primitive). Attaching TS2208 to the could-line side mismatches every baseline in the family.

- **Nested generic functions must inherit enclosing type params**: the `checkTypeAssignabilityInStatements` FunctionDeclaration arm passes `outerTypeParams = typeParams` — dropping it makes every bare-TP mismatch check silently never fire inside nested generic fns. Union-constraint rule: a constraint chain reaches a target tp iff ALL union members do (`tpConstraintChainReachesTp`).

- **Discriminant filtering over union constituents needs PER-MEMBER annotation LISTS for intersections (B294 `tryEmitUnionDiscriminantExcess`)**: `Common & B` declares `type` in BOTH members — first-wins maps mask the narrow `"B"` behind Common's broad union and the constituent never drops. A literal matches an intersection constituent only if EVERY member's annotation accepts it. Boolean literal discriminants compare by AST text (no Type.BooleanLiteral exists).
- **Nested excess-property TS6500 related info is CALL-ARG-path only (B220)**: tsc attaches "The expected type comes from property 'X' which is declared here on type 'Y'" to nested TS2353/TS2561 only when the EPC descends from a call ARGUMENT (contextual typing through a signature) — var-decl/assignment nested EPC stays related-free (nestedFreshLiteral) and union-parent hops stay related-free (nonObjectUnionNestedExcessPropertyCheck). `checkExcessProperties`'s `buildNestedRelated` flag is set only at the two arg-loop call sites; don't enable it elsewhere. Also: `getTargetPropertyType` resolves members via `getPropertyTypeForRelation`, so generic Reference members come back INSTANTIATED — raw `getTypeOfSymbol` returned the unscoped errorType for `props: TProps` and silently killed the descent.
- **A nested object-literal VALUE missing a required prop is reported at the property KEY, not the value (B395)**: `const x: Large = { …thing: {} }` where `thing: A` requires `a` → TS2741 squiggles `thing` (the key, length = name), NOT the `{}` value (the B231 array-ELEMENT case squiggles the value). `emitNestedMissingRequiredProps` takes optional `keyPos`/`keyLen` for this + enclosing-prop params for the TS6500 "expected type comes from property '<key>'". ### Overload resolution gotchas

- **TS2769 with ALL overloads failing — best-matching-overload collapse (B418a, `countFailingArgDiagnostics`/`reported` in `checkArgumentsAgainstOverloads`)**: when an array-literal arg fails ≥2 ELEMENTS against some overload, tsc reports ONLY the overload with the FEWEST per-element diagnostics (the single best candidate) and anchors at that element (`chooseOverload`'s `max>1 ? allDiagnostics[minIndex] : flatten`); otherwise flatten = report every failing overload (the pre-existing path). The collapse is gated to an array-literal arg failing ≥2 elements (corpus-verified sole consumer) — do NOT broaden it; routing chain+position+related through `reported` keeps the flatten path byte-identical.
- **`Type.TypeParam` instances are interned PER AST POSITION, so identity comparison across resolution sites FAILS (B199)**: a signature's `T` (interned at the TypeParameter node) and the SAME `T` inside an annotation like `Iterator<T, boolean>` (resolved through a different path) may be DISTINCT instances — compare by kind + `symbol?.name`, never by `===`, when matching a sig TP against a Reference's resolvedTypeArguments. ALSO: a namespace-local interface sharing an embedded-lib interface's name (e.g. `Underscore.Iterator` vs lib `Iterator`) resolves the REFERENCE's `target.symbol` to the LIB symbol — verify the resolved decl's shape (TP count) and fall back to scanning the file's namespace bodies for the local InterfaceDeclaration before trusting it.
- **Lazily-resolved symbol kinds must store their shell type in `symbolTypes` BEFORE signature resolution (in-progress sentinel, same pattern as the getDeclaredTypeOfClassOrInterface cache-before-bases rule)**: a self-referential annotation (`function foo(): typeof foo`) otherwise recurses to StackOverflowError, which is SILENTLY swallowed by consumers' catch — symptom is zero diagnostics for the whole statement, not a crash.

- **`tryInferSingleTypeParamFromArgs` MUST publish the WIDENED type into the inference mapper, never a literal (tried, REVERTED -2)**: the mapper feeds `currentLocalTypes`, JS-emit, and contextual `this`-binding; a literal leaks into a shared type cache causing ORDER-DEPENDENT regressions in UNRELATED JS-emit tests (target passes in isolation, fails in the full suite). Literal-vs-widened display for TS's fixed-type-parameter rule must be computed LATE, at the TS2339/TS2345 emission site only — do NOT change what the mapper publishes to fix a display-only mismatch.
- **`typeMentionsTypeParam` does NOT recurse into function-shaped `Type.Object`** — it only detects a TP in a callback's IMMEDIATE param/return position. For NESTED function types (`b: () => (a: T) => void`) use `tparamMentionedInFunctionTypeDeep` (descends call/construct sigs, Type.id cycle-guard).
- **Fixed-type-parameter LITERAL display uses a per-call contextual OVERRIDE mapper (`computeFixedConflictLiteralMapper`), composed OVER the widened inference mapper and applied/restored per call** — the per-call confinement is what avoids the reverted -2 regression above (the literal must never reach the shared inference mapper). Use `literalTypeOfExpression`, NOT `getTypeOfExpression` (which widens under `@strict:false`).
- **`isSimpleCheckableType` NOT used for overload resolution**: For TS2769, `allArgumentsMatch`/`getFirstArgumentError`/`getFirstFailingArgPosition` check ALL types (including objects, arrays) — not just primitives. The `isSimpleCheckableType` guard is only for single-signature TS2345 checking.
- **Generic type-reference element comparison in `structuredTypeRelatedTo`**: When `source` and `target` are both `Type.Reference` with the **same target interface** (`source.target === target.target`), compare resolved type arguments directly (covariant: each source arg assignable to the matching target arg) instead of full structural comparison. Otherwise `objectTypeRelatedTo` passes trivially because member types with unresolved type params resolve to `errorType` and built-in lib methods resolve to `anyType`. **Skip the shortcut when any target arg is `void`** — the void-return-type rule (a signature returning T is compatible with one returning void) applies transitively when a type arg appears in a covariant return position (e.g. `interface B<T> { x(): T }` — `B<number>` must be assignable to `B<void>` for method-override checks to pass). Falling through to structural comparison preserves the prior trivial-pass behavior for void-arg refs. `getPropertyElaborationChain` emits the matching "  Type 'A' is not assignable to type 'B'." chain line for the first failing arg pair. Cycle detection for self-referential generics (`interface List<T> { next: List<T> }`) is handled by `relationComparisonStack` in `checkTypeRelatedTo`.
- **Generic overload guard**: Skip `checkArgumentsAgainstOverloads` when any signature has type parameters. Without generic type argument inference, parameter types resolve to `errorType` and produce false positive TS2769.
- **MethodDeclaration typeParameters**: Must include type parameters from `md.typeParameters` when creating Signatures for interface method overloads — the generic guard relies on `sig.typeParameters` being populated.
- **TS2793 conditional on implementation match**: Only emit "implementation would have succeeded" when `allArgumentsMatch(args, implSig)` returns true for the implementation signature. Otherwise the implementation may also reject the arguments (e.g., `foo({a:any}[])` still requires property 'a'). In the arity-filtered single-overload path, use the same `allArgumentsMatch` check — don't blindly attach TS2793 to TS2345.
- **TS2793 gates call `allArgumentsMatch(..., bivariantFnParams = true)` under `strictExplicitlyFalse`** (TS treats method params bivariantly when strictFunctionTypes is off, so `(x: 'bye') => number` is accepted by impl param `(x: string) => number`); the overload-resolution match itself MUST keep the default contravariant check or overloads get mis-selected. Bivariant fallback fires only for anonymous Type.Object pairs with non-empty `callSignatures`.
- **Literal type widening in error display**: `getWidenedLiteralType` maps `true`→`boolean`, `false`→`boolean`, string/number/bigint literals→base types. Used in TS2769 error messages but NOT in type checking itself.
- **TS2739 vs TS2740 code selection**: TS2739 for 2-4 missing properties, TS2740 for 5+. Both use the same "Type 'X' is missing the following properties from type 'Y': a, b, ..." message format. TS2741 is for single missing property only.
- **TS1184 accessor guard**: "Modifiers cannot appear here" (TS1184) fires alongside TS1042 only for `MethodDeclaration` in object literals, NOT for `GetAccessor`/`SetAccessor`. TypeScript only emits TS1042 for accessor modifier errors.
- **`collectMissingProperties` returns empty when source.members is null**: Anonymous function types from `() => T` set `Type.Object.callSignatures` only and leave `members = null`. Treating `members ?: emptyMap()` would report every target property as "missing" (e.g. `() => void` → `[string]` → ["0", "length"] → spurious TS2739). Returning empty forces the caller's TS2739/TS2741 gate to fall through to plain TS2322 "Type '() => void' is not assignable to type '[string]'." — kind mismatch, not property-missing. Mirrors `propertiesRelatedTo`'s `source.members ?: return targetProps.isEmpty()` short-circuit.
- **Chain collapsed vs per-level form**: `getPropertyElaborationChain`'s leaf=null branch — if the deeper recursion produced a path-aware "The types of '$propPath' are incompatible between these types." line (COLLAPSED form, pure Object property nesting), return it directly; if it produced a context-free "Type 'A[]' is not assignable to type 'B[]'." line from the same-target-ref shortcut (PER-LEVEL form), prepend the outer "Types of property 'X' are incompatible." line and indent deeper by 2 more spaces.
- **Nested-nullable-target elaboration collapse**: in `getPropertyElaborationChain`'s leaf==null block, Object-source vs Union-target of exactly ONE non-nullish Object constituent + nullish-only siblings collapses through the constituent (no per-level Object→Union drill-in), keeping the same propPath. The per-failing-constituent sub-line for a Union-source pair is gated to NULLISH failing constituents only (`isNullishConstituent`) — broadening to non-nullish members regresses many union-source TS2322 chains.
- **Array-vs-array outer TS2322 suppression for array literals**: Var-decl and assignment paths must skip the outer "Type 'X[]' is not assignable to type 'Y[]'." when `init`/`expr.right is ArrayLiteralExpression` and target is a `Type.Reference` to Array. `checkArrayLiteralElementExcessProps` and related walkers already emit per-element TS2322/TS2353 at the specific offending element; the outer diagnostic would duplicate them.
- **`getTypeFromTypeNode` cache bypass for context-sensitive resolution**: `nodeTypes` cache must be bypassed when ANY context-stack is active that affects type-name resolution (`currentTypeParamScope`, `inferenceNamespaceStack`, …). A type node may resolve to different `Type` values under different contexts, and a stale cache entry (e.g. `errorType` from an earlier eager pass before the context was active) would shadow the correct context-aware resolution. Any new "lazy resolution context stack" added in the future must be checked here too — failure mode is silent (cache hit returns wrong type, downstream type checks pass falsely).
- **Two DISJOINT namespace stacks**: `inferenceNamespaceStack` (type-name resolution) vs `propertyAccessEnclosingNamespaces` (property-access walker) — the walker deliberately does NOT push to `inferenceNamespaceStack` (value-position TS2576 FPs). A type-position resolution inside the property-access walker that needs namespace-local type names must bridge the innermost enclosing-namespace symbol onto `inferenceNamespaceStack` ONLY around that one `getTypeFromTypeNode` call (popped in `finally`; see `populateParameterLocalTypes`) — never for the whole body walk (reintroduces the TS2576 FP). Symptom of the gap: namespace-local-typed params silently resolve to errorType → no TS2339.
- **Lazy variable type inference must thread containing namespace**: Variables declared inside `namespace M { var x = ...; }` have `symbol.parent = M` set by the binder, but `getTypeOfIdentifier`/`getTypeFromTypeReference` don't have an AST-parent walk (no parent pointers in our AST). `getTypeOfVariableOrProperty`'s VariableDeclaration branch must `pushInferenceNamespaceFor(symbol)` before resolving annotations OR initializers so identifier/type-name lookups can consult the namespace's `exports`. Without this, namespace-internal references (e.g., `var inner; export var outer = inner`) silently bail to `anyType`, masking genuine type errors. The push covers both type annotations and initializers because both can reference namespace-local declarations.

### Inline source map gotchas

- **Inline source map uses output-to-source line matching**: `SourceMap.kt` generates VLQ mappings by matching output JS lines to source lines (not fixed offset). This handles cases where the emitter drops empty lines between statements. The Scanner tokenizes each matched line to find mapping positions.
- **VLQ mapping positions**: TypeScript maps every token start + identifier ends (pos + text.length). The `=` in variable declarations is NOT mapped. Semicolon-end (statement end) positions ARE mapped for all statement types. Keywords do NOT get end positions (only `SyntaxKind.Identifier`).

### Multi-file baseline gotchas

- **`tsconfig.json` not echoed**: The TypeScript test harness treats `tsconfig.json` as project configuration, not a source file. Never include it in the `sourceEchoes` list in `formatMultiFileBaseline`. Other JSON files (e.g. `tsconfig1.json`) ARE echoed.
- **Error baseline file ordering**: TypeScript's test harness reorders files in error baselines when the last `@Filename` file contains `require(` or `reference path`, or when `noImplicitReferences` is set. In those cases, the last file is moved to the front. This differs from JS baselines which always use `@Filename` order.
- **CRLF in test source files**: TypeScript test source files use CRLF line endings. `parseMultiFileSource` normalizes to LF early to avoid trailing `\r` characters causing extra blank lines in error baselines.
- **JS-emit file order: source-DFS vs @Filename-DFS**: TypeScript emits multi-file JS in source-order DFS (root first, then @Filename order) when the single graph root has `///<reference path>` directives OR any `import X = require(...)` (ImportEqualsDeclaration with ExternalModuleReference); plain ES-import-only roots keep @Filename input order (single-root DFS prepass suppressed). Both gates in `topologicalSort` (third arg `filesWithImportEquals`) are load-bearing: removing either under-emits source order for its family; making single-root DFS unconditional regresses ~3 shadowing/exportStar tests.

### Deprecation diagnostic gotchas

- **TS5101 vs TS5102 vs TS5107**: Three different deprecation codes. TS5107 = target/module/moduleResolution deprecations. TS5101 = outFile/baseUrl/downlevelIteration deprecations (still functioning). TS5102 = removed options (out, charset, keyofStringsOnly, noImplicitUseStrict, etc.) with message "has been removed. Please remove it from your configuration."
- **`const enum` at statement level**: `parseStatement()` must check for `const enum` (not just inside `export`/`declare` contexts) — otherwise `const enum E {}` is misparse as `const` variable named `enum` + expression `E` + block.

### Checker diagnostic gotchas (TS2454/TS2564/TS6133)

- **`strict: false` suppresses TS2454/TS2564**: TypeScript test baselines expect these diagnostics by default, but NOT when `@strict: false` is explicitly set. Use `options.strictExplicitlyFalse` to distinguish default-false from explicit-false.
- **Definite assignment assertion `!`**: `var x!: Type` and class property `x!: Type` skip TS2454/TS2564 checking. Check `exclamationToken` on both `VariableDeclaration` and `PropertyDeclaration`.
- **Ambient contexts**: Skip TS2454/TS2564 in `declare` namespaces, classes, and functions. A class inside a `declare namespace` is ambient even if the class itself doesn't have `declare`.
- **TS6133 non-module files**: Don't check file-level unused declarations in non-module files (no imports/exports). Only check inside namespaces, functions, blocks.
- **TS6133 write-only**: Assignment targets (`x = value`) are NOT reads. Left side of `=` operator is write-only. Compound assignments (`x += 1`) ARE reads.
- **Flow.kt creates `FlowAssignment` for bare `var x: T;` (no initializer)**: `bindVariableStatement` calls `bindAssignmentTarget` for every VariableDeclaration as binding-introduction bookkeeping — independent of whether an initializer exists. Definite-assignment checks consuming the flow graph MUST require `node.initializer != null` on a VariableDeclaration FlowAssignment to count it as a real assignment, otherwise the declaration itself masks every TS2454 candidate that walks back through it. Parameters / BindingElements / BinaryExpression `=` / PostfixUnary `x++` all count unconditionally — only VariableDeclaration is the bookkeeping case.
- **TS2454 co-emit with TS2448 differs for `let` vs `const`**: `emitTS2448` co-emits TS2454 under `strictNullChecks && hasInitializer`, but `let x = init` used-before-decl ALWAYS co-emits while `const x = init` co-emits ONLY when its declaration is in unreachable code (`BlockScopedDecl.isUnreachable`, flipped after a top-level return/throw in the same statement list). Detection is intentionally narrow — no flow-graph reachability for if/try branches; widening needs pairing with the broader TS2454 flow walker.
- **`FlowLoopLabel.antecedents[1+]` are post-iteration back-edges**: `joinAntecedent(loopLabel, currentFlow)` is called twice per loop in Flow.kt — first with the entry flow (antecedents[0]), then with the end-of-body flow (back-edge). Continue statements add additional back-edge antecedents. For walks that use OR-semantics over antecedents (e.g. "is there ANY reaching path with assignment evidence?"), naively `.any { ... }` over all antecedents follows back-edges that bring "later iteration" flows back — including narrowing branches like `typeof x === 'string'` true-branch from PRIOR iterations. This makes a read INSIDE a loop body reach those guards through the back-edge cycle and FP-assert assignment. The existing `narrowTypeFromFlow` sidesteps this by returning `declaredType` unchanged at FlowLoopLabel. For OR-semantics walks, only follow `antecedents[0]` (the loop entry). For AND-semantics walks (does EVERY path assign?), the same restriction is needed for soundness.
- **Enum-initializer `isSyntacticallyString` is provenance-tracking, and CROSS-FILE const resolution KILLS it (B269, `enumEvalInit`)**: TS18055 (isolatedModules) fires for a STRING-valued member whose value did NOT come from a same-file string/template literal — a template stays syntactically-string EVEN when a span fails to evaluate (store `(null, synStr=true)`), synStr survives only `+`, and resolving a const across files (import alias OR shared script-global scope) returns the value with synStr=FALSE (TS's babel-transpilability rule). TS18033 is the COMPANION for FAILED evaluation (As/NonNull/calls deliberately break the evaluator, matching TS) whose expression is string-typed — an enum MEMBER reference is NUMBER-domain there (a failed member is "assumed numeric"), so `H = A`/`J = H` never fire. Don't "fix" the evaluator to see through `as`/`!` casts — the failure is load-bearing for TS18033.

### Test assertion gotchas

- Avoid partial `assert("x" in result)` — always assert the full expected output.
- **Test ordering sensitivity**: Adding new checker code that increases diagnostics can cause deterministic failures in unrelated JS emit tests — tests pass individually but fail in the full suite. Always run the full suite to verify no regressions.

### TS2304 unresolved name checking gotchas

- **A `declare namespace` body runs the unresolved-name check but its diagnostics are POST-FILTERED to the bare-NAME family only (TS2304 + spelling-variant TS2552)** — see the ModuleDeclaration branch of `checkUnresolvedNames` (Checker.kt ~18061). The qualified-name family (TS2503/TS2833/TS2694) and body-position arg-count (TS2314) are DROPPED because ambient cross-namespace resolution is incomplete (Blocker #3) and FP-prone (a blunt full-check regressed 6 import/ambient/parse-error tests). Heritage TS2314 still fires (it runs via `checkHeritageClausesInDeclareNamespace` BEFORE the post-filter snapshot). Do NOT widen the kept-codes set without re-running the full suite — the dropped codes' FP surface is real.
- **Kotlin property initialization order**: Properties declared after `init {}` have default values (0 for Int, false for Boolean) during init execution. **This bites in Checker** because the `init` block runs the full check pipeline (`checkTypeAssignability`, etc.) — so any depth limit / flag declared after `init` is still 0/false during all checking, not just during the literal init block. Mitigations: (a) declare the property BEFORE `init` (used for `maxCheckDepth`, `checkDepth`, `strictNullChecks`), or (b) use a companion-object `const val` (used for `NARROW_MAX_DEPTH`) — compile-time constants don't depend on instance init order.
- **KNOWN_GLOBALS coverage**: ~400 lib.d.ts names in the companion object. Missing a global causes false positive TS2304. When adding new globals, check both value and type positions.
- **The root `fileScope` seeds `KNOWN_GLOBALS` into `scope.names`, so `scope.has(name)` is ALWAYS true for any global** (`NaN`, `Object`, `Array`, …). An "is this the GLOBAL X vs a local shadow?" check therefore CANNOT use `scope.has(X)` — use `NameScope.hasLocalShadow(name)`, which is true only when the name is bound in a NON-root scope (a real param/local/block binding).
- **KEYWORD_IDENTIFIERS**: Our parser produces `Identifier` nodes for `this`, `super`, `true`, `false`, `null`, TypeScript type keywords (`any`, `number`, `string`, etc.), and access modifiers (`public`, `private`, etc.). These must be excluded from TS2304 checking.
- **Binder scope model**: The binder only creates file-level symbol tables. Function parameters, catch variables, and block-scoped declarations are NOT in the binder's symbol table. The TS2304 checker maintains its own scope chain.
- **Test generator only processes `.ts`**: `.tsx` files are excluded from test generation (`f.extension == "ts"` in build.gradle.kts). This means JSX-related diagnostics (TS7026) are untestable.
- **`arguments` not a global**: Don't include `arguments` in KNOWN_GLOBALS — it's only available inside non-arrow functions via the `hasArguments` flag on NameScope.
- **`var` hoisting for TS2304**: `var` declarations inside nested blocks/loops are function-scoped. `collectHoistedVarNames` recursively finds them and adds to the enclosing scope.
- **`isIdentifier()` vs `isIdentifierToken()`**: Inside `scanner.lookAhead {}`, use `isIdentifierToken(scanner.getToken())` not `isIdentifier()` — the latter checks the Parser's cached `token` field which isn't updated inside lookAhead.

### TS2345 argument type checking gotchas

- **The call-type walker types only CALLABLE function-local vars**: `checkCallTypesInStatement`'s VariableStatement branch populates `currentLocalTypes` only for an ANNOTATED local whose resolved type is `Type.Object` with non-empty `callSignatures`. The callable gate is load-bearing — populating ALL local var types would broadcast arg-checking and receiver-type lookups across every function with annotated locals (huge FP surface).
- **TS2345 standard-path literal display: widen the ARG unless the PARAM is a literal**: at the main arg-vs-param mismatch emit, display `getWidenedLiteralType(argType)` normally, but the RAW argType when the param type is itself a literal (`f(x:123)` called `f(true)` → 'true'). Do NOT globally widen (regresses the literal-target case) nor globally preserve (wrong for base targets). `getWidenedLiteralType` is a no-op for non-literal args, so object/named/reference displays are untouched.
- **Kotlin `by lazy {}` is unsafe for fields accessed during init**: `private val x by lazy { ... }` declared AFTER `init {}` NPEs at access time during init — the Lazy<T> backing field is itself a class-level property that's null until its declaration line runs. Symptom: `Cannot invoke "kotlin.Lazy.getValue()" because "<local1>" is null`. Fix: replace with a `private fun foo()` + `private var fooCache: T? = null` declared BEFORE init; null-check inside the function. Both `var x: T? = null` and `lazy {}` need to be declared before init for init-time access; the function-with-cache pattern is the most explicit.
- **Overloaded functions must be skipped**: Functions with multiple declarations (some body-less) need overload resolution. Detect via `symbol.declarations` having body-less `FunctionDeclaration`/`MethodDeclaration`.
- **Overload-arity TS2554**: `collectFuncDecls` accumulates the min/max arity RANGE across overload SIGNATURES and EXCLUDES the impl signature (only overload sigs are externally callable, matching TS; first signature's params kept for TS6210). TS2554 fires only when argCount is outside EVERY overload's range — within any range, defer to type-based TS2769. With explicit type args, arity is checked against only the generic sigs accepting that type-arg count (TS6210 only when that subset is a single sig). Only top-level/namespace Identifier-callee functions are tracked — method-call overloads are NOT in `funcParams`.
- **Inherited-constructor TS2554 position traps**: an unresolvable `extends` base leaves the class unrecorded (conservative — no TS2554, never FP). The NewExpression TS2554 squiggle must span the WHOLE `new X(...)` — pass the NewExpression node (NOT `expr.expression`) to `emitTS2554TooFew`/`emitTS2555TooFew`, and pass `info.parameters` so TS6210 fires. **TS6210 anchors at `Parameter.pos`, NOT `param.name.pos`** — `Parameter.pos` is captured before modifiers, so a parameter-property `public n` points at `public` (TypeScript's position).
- **Enum-receiver missing-member TS2551 MUST gate on `isPropertyAccessShape && !isNumericProp`**: a numeric ELEMENT access `E[0]` is a valid enum reverse-mapping (number→name) — without the gate it FP-emits TS2339 on `MyEnum[0]`. Fires only for pure `SymbolFlags.Enum` (no Module flag — const-enum-holding namespaces are handled by the Module branch).
- **Conservative parameter type checking**: Only check TS2345 when the parameter type is a simple/primitive type (string, number, boolean, void, null, undefined, never, bigint, symbol, and their literal variants). Checking against object/interface/union/intersection parameter types causes FPs due to incomplete structural comparison and missing generic instantiation.
- **`getArrayType` returns a real `Type.Reference(Array, [elementType])`**: array-method-callback PARAM types flow through `resolveGenericPropertyType` + `substituteOuterTypeArgsInGenericFnObject`, so `arr.map(x => x.foo)` types `x` correctly (TS2339 fires). Still NOT inferred: the callback's RETURN type from the lambda body — `arr.map(...)` resolves to `any[]`, not `U[]` (needs body-driven generic return inference / Blocker #2). The legacy empty-Object array exists only behind `isArrayLikeType` guards.

- **`null`/`undefined`/`never` → `void 0`**: Serialize as `VoidExpression(0)`, not `Object`. `never` always excluded from unions; `null`/`undefined` only filtered when `!strictNullChecks`.

- **`isValueExport` returns `true` (safe default)**: Only return `false` when definitively type-only (TypeAlias, Interface, non-instantiated namespace).
- **Same-display-name interfaces from DIFFERENT files render TS2741 with `import("file").T` qualification** (`getSymbolImportName`, identity-search of `binderResults.locals`); fires only when both sides are different `Type.Interface` symbols resolving to different declaring files — never for lib symbols or nested-namespace exports.
- **Same-named `export interface` in different files MERGES via `mergeSymbolTable`**: At checker init, `mergeSymbolTable(globals, result.locals)` is called for every binderResult. When two files both `export interface F`, the second file's F is merged into the first's symbol — `existing.declarations.addAll(symbol.declarations)`. Downstream, both files' `let a: A.F` and `let b: B.F` resolve through the SAME merged symbol, and after `resolveStructuredTypeMembers` both Type.Interface instances carry the UNION of properties from all declarations. Consequence: structural disjointness checks (`b53.2`-style "no overlap" TS2367) silently never fire because the "missing" property has been merged into both sides. This is part of **Blocker #3 (Cross-file global scope conflation)** — fixing requires per-file scope construction with only own-file declarations in own-file resolution. Workaround patterns: diagnostics that compare ENTIRE display strings (TS2741 in B53.1) work because separate Type.Interface IDs survive merging; diagnostics that compare member-sets do not.
- **`LIB_MIN_TARGET` member filtering applies in `resolveInterfaceMembers`'s per-decl loop** (gated `decl in builtinLibDecls` + `options.target < minTarget`); user augmentations of the same interface pass through UNFILTERED. Verify new entries against `typescript-repo/src/lib/lib.esXXXX.*.d.ts`. Symptom of a missing entry: a SWAP diff that is JUST a count change in an "and N more" missing-property display. (See also the round-135 Lib-suggestion section for SOFT entries and `libFeatureAvailable`.)
- **The embedded lib deliberately simplifies most Array callback methods to `=> any`/`any[]`** — only `map`/`reduce`/`reduceRight` are generic and `every`/`filter` carry the real type-predicate overload pairs (see BUILTIN_LIB_SOURCE). Promoting ANOTHER Array method to generic is a BROAD lib change touching every array-method call — full-suite verify.
- **Two `implements Array` tests have CONTRADICTORY lib-snapshot baselines (Blocker #4)**: `implementArrayInterface_ts` (`MyArray<T> implements Array<T>` declaring ~25 members) expects ZERO TS2420 missing-property errors (its baseline predates `find`/`findIndex`/`fill`/`copyWithin`/`flat`/`flatMap`/`keys`/`values`/`entries` being in `Array`), while `genericArrayExtenstions_ts` (`ObservableArray<T>` declaring only `concat`) expects "length, pop, push, join, and 24 more" = 28 missing — which REQUIRES the FULL current member set. The TS2420 FP on `implementArrayInterface` is therefore un-flippable surgically. B86.13 DID flip its other two FPs (the `filter` TS2416 FP via the predicate overloads; the `every` TS2416 message via the overload-aware predicate-mismatch detector in `checkClassPropertyOverrides`) — only the TS2420 remains.

A sibling overload returning a PLAIN type (`(...): S[]`, not `this is`) does NOT trigger it.
- **Destructured `[x]`/`{x}` params are NOT in `currentLocalTypes`** (`populateParameterLocalTypes` registers only Identifier params there; binding names go to `currentParamBindingNames` instead). Pairs with B54.6's accessor-pair declaration merging.
- **The varTypes Identifier-RHS same-base-parameterized-ref check is gated to ≥1 PRIMITIVE type arg (B54.9) — do not loosen**: named-type args regressed (structurally-identical interface args `C<X>` vs `C<Y>`; `Promise<Foo>` vs `Promise<Bar>` covariance). `inferSimpleExprType` itself deliberately skips Identifier variable-type lookup (source comment at the `else -> null`).

### TS2454/TS2564 gotchas

- **`any` type skips checking**: Variables/properties typed as `any` skip TS2454/TS2564.
- **`var` declarations**: TypeScript DOES check `var` for TS2454 (when strict) — only `any`-typed vars are skipped.
- **`ExportAssignment` is a use site**: `export = Foo` must be checked in `checkUsesOfUninitialized`.
- **Abstract classes still need TS2564**: Only `declare` classes are exempt, NOT `abstract`.
- **TS7030 guard**: Requires `strictNullChecks || noImplicitReturns`. TS2355 fires regardless.
- **TS2366 requires strictNullChecks**: TS2366 ("Function lacks ending return statement and return type does not include 'undefined'") fires ONLY under `strictNullChecks`. Without it, use TS7030 ("Not all code paths return a value"). Do NOT gate TS2366 on `noImplicitReturns` alone.
- **TS2355 for `undefined` in unions**: TS2355 fires for `function f(): undefined | T {}` (where T is non-void) when there are no return statements — `undefined` in a UNION does NOT satisfy "must return a value", only as a BARE `undefined` keyword (or `Promise<undefined>` for async) does. The classification in `checkBodyForImplicitReturn` (Checker.kt): `KeywordTypeNode(undefined)` and `TypeReference(Promise<KeywordTypeNode(undefined)>)` for async → "pure-undefined" (suppress all checks); UnionType-containing-undefined or `Promise<UnionType>` → "nullable" (TS2355 fires when no returns; TS7030 falls through when mixed returns).
- **`NumericLiteralNode` in method names**: All method-name extraction functions must handle it, not just `Identifier` and `StringLiteralNode`.
- **Bare specifier TS2882**: Always emit for bare (non-relative) specifiers except in AMD/System/UMD modules.

### TS1210 class strict mode gotchas

- **TS1210 vs TS1100**: TS1210 fires for `arguments`/`eval` in class bodies (always strict). TS1100 fires in external strict mode contexts (functions, modules). TypeScript NEVER emits both for the same node — TS1210 takes priority in class bodies. Suppress TS1100 inside class bodies for these names.
- **`emitDeclarationOnly` still needs checker**: Multi-file compilation with `emitDeclarationOnly` must still parse/bind/check files for diagnostics like TS1210. But use `declarationOnly = true` to limit checks — running the full checker produces FPs like TS6131 that TypeScript's declaration-only mode suppresses.
- **`isAlwaysTruthyExpr` vs `isAlwaysTruthyForOrExpr`**: In `||` contexts, TypeScript flags object-like expressions (function, arrow, object, array, class, regex) and non-empty string literals. Numeric literals and `new` expressions are NOT flagged in `||` but ARE flagged in `if`/`else if` conditions.

### Kotlin idioms

- **`*/` inside KDoc terminates the comment**: A `/** ... */` doc comment ends at the first `*/`. Embedding `*/` (e.g. when documenting a JSDoc pattern) silently breaks the rest of the declaration — a data-class body following a broken doc comment surfaces as a cascade of confusing errors like "Modifier 'override' is not applicable to 'local variable'", "No parameter with name 'pos' found", "Unresolved reference 'jsDocTagEnd'". Reword to "comment-close" or escape as `*\/`.
- **Kotlin block comments NEST — a literal `/**` *inside* a KDoc opens a nested comment level (B151)**: writing the JSDoc string `/** @overload ... */` inside a `/** ... */` doc comment makes the inner `/**` open a NESTED block comment, so the doc comment's closing `*/` only drops back to depth 1 and the comment runs to EOF → `Syntax error: Unclosed comment` at the last line + a cascade of "Unresolved reference" errors for class members BEFORE the doc comment (the whole class fails to parse). This is DISTINCT from the `*/`-closes-early gotcha above: here it's the `/**` opener that bites. When documenting JSDoc tag syntax in a KDoc, never write a literal `/**` (or `/*`) — describe it as "a JSDoc comment" or use single-line `//` comments.
- **No non-stdlib dependencies in `commonMain`**: The project targets Kotlin Native (in addition to JVM/JS), so `commonMain` must use only `kotlin.*` and `kotlinx.*` packages. No `java.*`, no `BigDecimal`, no JVM-only types. Use Kotlin's built-in numeric types and stdlib math (`kotlin.math.*`).
- **Enum context resolution** (Kotlin 2.1+): When the expected type is an enum, use unqualified entry names — write `Equals`, not `SyntaxKind.Equals`. This applies to `when` branch conditions, named arguments (`operator = Equals`), comparisons (`flags == VarKeyword`), and any other position where the enum type is inferred. Caveat: if a data class has the same name as an enum entry (e.g. `LabeledStatement`), keep the `SyntaxKind.` prefix to avoid ambiguity.
- **`in 0..<x` range checks**: Prefer `pos in 0..<end` over `pos >= 0 && end > pos` for range validation — uses Kotlin's `rangeUntil` (`..<`) operator for exclusive upper bound.
- **No JVM-only APIs in `commonMain`**: `Map.putIfAbsent` → use `getOrPut`; `Math.pow` → use `kotlin.math.pow` extension; `RegexOption.DOT_MATCHES_ALL` → use `[\s\S]` in the pattern (B259). `./gradlew compileKotlinJvm` does NOT catch these — it compiles only the JVM target. Always use Kotlin stdlib equivalents for multiplatform compatibility.
- **`when` guard conditions** (Kotlin 2.1+): Use `when (val ch = x) { '/' if condition -> ... }` instead of `when { ch == '/' && condition -> ... }`. The `if` guard after the match value keeps pattern matching readable and avoids nested `when`/`if` blocks.

### Execution protocol

PLAN-PHASE-4.md contains the **live QUEUE** under the heading `## Phase 16 — Fundamental Type System Features` → `### QUEUE — prioritized by unblocking potential, then by implementation cost`. (Earlier `### QUEUE` sections in the file are archived from prior phases — do not work them.) Live session notes also live under that heading, with the most recent at the top. Default order is top-to-bottom, **fixing as many items per session as the budget allows** — do not stop after a single item if there is remaining context and more tractable work ahead. The outer loop:

1. Pick the first unchecked (`- [ ]`) item in the live queue (or next unfinished sub-step of an `IN PROGRESS` item). If the top item appears blocked on missing infrastructure, **do NOT skip it** — instead, promote the unblocker to the top of the queue and work that (see autonomous-decision policy below). The original item stays unchecked and gets picked up automatically once the unblocker lands. Skipping past a blocker is reserved for the narrow user-policy cases listed under "Guardrails."
2. Implement it — the item describes the deliverable.
3. Run the full suite (`rm -rf build/test-results/jvmTest/binary && ./gradlew jvmTest 2>&1 | grep -a "tests completed"`).
4. Verify no regressions from the currently passing test count.
5. Check off the item (`- [x]`), **bump the test count in STATUS.md** to reflect the new passing total, add a session note to PLAN-PHASE-4.md (under the live notes heading, most recent on top), add a CLAUDE.md gotcha if applicable, **commit and push** (one commit per sub-step — keeps history bisectable and lets the next agent pick up mid-stream without re-running everything). STATUS.md drift is a real failure mode — past sessions committed `(+N)` work without bumping the count, so the next agent saw a stale baseline. **Trim-on-write (the anti-balloon rule)**: when bumping STATUS.md, keep only the ~5 most-recent round notes — move older ones to STATUS-HISTORY.md in the same commit; when adding a session note to PLAN-PHASE-4.md, if more than ~10 rounds are live, move the oldest to PLAN-PHASE-4-HISTORY.md in the same commit. Both files ballooned (160 KB / 1.7 MB) before the 2026-06-10 trim because sessions appended without trimming.
6. **Loop back to step 1** and pick up the next item. Keep going until one of these stop conditions:
   - Context budget is running out — finish the current item cleanly, commit, then stop.
   - Every remaining queue item is gated on user-policy decisions (Guardrails) AND no in-scope unblocker work remains. This should be rare — under the promote-unblocker default, blockers turn into queue items, so the queue rarely runs dry.
7. End the session with a concise summary of items completed, unblockers promoted (with what they unblock), items left pending user decisions, and net test count delta.

**Autonomous-decision policy (when an item appears blocked):**

When an item can't be implemented surgically — e.g. the diagnostic relies on infrastructure that doesn't exist yet (super-keyword resolution, full flow-graph, generic argument inference) — **promote the unblocker, do not skip the item**:

- **Promote-unblocker (default)**: identify the smallest concrete infrastructure piece that would unblock the item, insert it at the TOP of the queue with a one-line description and a back-pointer to the original item (and any other items it would also unblock — list them). Then start work on the unblocker. The original item stays unchecked; it gets picked up automatically on a future loop. Cross-phase work (binder + checker together, scope-chain restructuring, new cache layers) is in scope — that is exactly the work this policy exists to drive.
- **Decompose first if large**: if the unblocker is itself a multi-step change, split it into the smallest standalone sub-step that lands as a single commit without regressions, queue that, and only that. Do not attempt the whole infrastructure piece in one pass. Subsequent sub-steps get queued as separate items as the work progresses.
- **Time budget per attempt**: cap each attempt at one full-suite verification cycle. If it regresses, revert. After revert, you may either (a) try a different decomposition for the same unblocker, or (b) move to the next queue item — but record both attempts in the session note. Do not iterate more than twice in one session on the same regressing approach; if neither works, write up what you learned (which paths broke, what the underlying coupling is) and queue a follow-up "investigate X" item.
- **Skip is reserved for Guardrails only**: the only legitimate skip is when the unblocker requires a user-level decision listed under Guardrails below. For those, leave a `BLOCKED-PENDING-USER:` marker on the item with a one-paragraph proposal for the user to react to, then continue with the next queue item. Do NOT end the session.
- **No silent abandonment**: every promote/decompose/skip writes a session note (PLAN-PHASE-4.md, most recent on top) with root cause, what was attempted, and what landed. Never leave an item half-done in the working tree.

**Anti-loop rule — recon-only sessions are a protocol failure:**

A "recon-only session" is one that runs `find_candidates.py --fresh`, gets `0/0/0` (or similarly empty), spot-checks a handful of candidates, confirms they are all architectural, commits a `chore(status): refresh ... empty pool` note, and ends without landing any code change. **This is not a legitimate session outcome when the queue contains unchecked Blocker items.**

- **The `0/0/0` "exhausted" reading is almost always FALSE (fixed 2026-05-30).** The plain `find_candidates.py` EXTRA/MISSING/SWAP buckets only scan tests that ALREADY emit a parseable `error TSxxxx` line — historically ~33 of >1000 failures. The other ~70% (tests where we emit NOTHING, plus pure JS/decl/sourcemap output diffs) were structurally invisible, which is what manufactured the recurring "pool exhausted" illusion across ~20 rounds. The tool now has a **`--none`** bucket (baseline expects diagnostics, we emit none — recovered by reading the `*.errors.txt` baseline, grouped by code, fewest-error-lines-first = most tractable) and an **`--output`** bucket. **The bounded NONE tail IS the live surgical pool** (TS2307 module-resolution, TS2403, TS2367, TS2540, TS2554, TS2688, TS2344, TS2305, TS2551/2552, decl-emit TS4023/4025 …). See PLAN-PHASE-4.md § "STRATEGIC MAP of the remaining failures" for the current breakdown.
- **Hard rule**: the pool is "exhausted" ONLY when `find_candidates.py --fresh` (EXTRA/MISSING/SWAP) **and** `find_candidates.py --none --fresh` (the bounded-code NONE tail) **and** `find_candidates.py --output --fresh` are ALL dry. If any has fresh bounded candidates, work them — do NOT jump to an architectural blocker or commit a recon note. Only when all three are genuinely dry AND the queue has an unchecked `- [ ]` Blocker substep do you start that substep in the same session.
- **Diagnostic signal**: before starting a session, run `git log --oneline -10`. If three or more of the last 10 commits match `chore(status): refresh ... empty pool` (or equivalent recon-only commits), the queue is mis-structured — the agent in earlier sessions failed to promote a blocker to a checkbox. **Your first action is to fix the queue**: open PLAN-PHASE-4.md's "Known architectural blockers" section, pick the highest-yield blocker that has no corresponding `- [ ]` queue item, decompose it into the smallest standalone substep, insert it at the top of the QUEUE, commit that restructure (`chore(queue): promote Blocker #N to queue item`), and only THEN start work on it.
- **Recon is allowed as part of step 1**, not as a session deliverable. If a recon turns up surgical candidates, fine — work them. If it doesn't, that's the trigger to attack the next Blocker substep, not to wrap up.
- **Forbidden commit message patterns** when the queue has unchecked Blocker items: `chore(status): refresh post-N.N recon`, `... empty surgical pool`, `... N+ consecutive empty pool`. These are signals that the protocol has failed. The only acceptable session-end commits are (a) a feature commit landing real code, (b) a `chore(queue): promote ...` restructure that prepares the next session, (c) a `chore(maint)`-class action like a stale-skip-log audit when one is genuinely warranted (≤ once per ~5 sessions), or (d) a revert of a regressing attempt.
- **STATUS.md "consecutive empty pool" counters are a code smell, not a metric**: bumping `19+ → 20+ → 21+ → 22+` across consecutive sessions means each of those sessions failed the anti-loop rule. If you find such a counter on entry, treat it as the diagnostic signal above and fix the queue first.

**Guardrails requiring user input** (do NOT decide autonomously):
- Build system changes (Gradle config, dependency add/remove/upgrade, Kotlin version bump).
- Test-generation pipeline changes (`generateTypeScriptTests`, baseline format, skipped-tests log structure).
- Re-enabling currently-disabled test categories (e.g. `.errors.txt` → +9k tests).

**Other rules:**
- **Do NOT switch items** mid-task — finish the current item (commit + push) before starting the next.
- **Commit between items** — never bundle two unrelated sub-steps into one commit. Each committed sub-step leaves the repo in a clean state for the next agent.
- **Analysis items** (item 0) should produce written artifacts (design docs, categorized lists) before any code is written.
- **No regressions** — the currently passing tests must continue to pass after every change. Re-run the full suite between sub-steps; a +1 / -2 swap is still a regression.
- **Full-suite run caveat**: a clean JVM test run takes ~4-6 minutes. Budget accordingly when deciding whether to attempt another item.

## How to run tests

```bash
# Full suite (always clean binary cache first — stale cache inflates failure count):
rm -rf build/test-results/jvmTest/binary && ./gradlew jvmTest 2>&1 | grep -a "tests completed"

# Single test (get expected vs actual diff):
rm -rf build/test-results/jvmTest/binary && ./gradlew jvmTest --tests '*.<TestName>*' 2>&1 | grep -a -A 40 "message" | head -50

# Candidate finder (must have fresh full-suite XMLs first):
python3 scripts/find_candidates.py --fresh              # EXTRA/MISSING/SWAP, hide skip-logged
python3 scripts/find_candidates.py                      # all buckets, with [SKIP] markers
python3 scripts/find_candidates.py --none --fresh       # tests where we emit NOTHING (the real pool)
python3 scripts/find_candidates.py --none --fresh --code TS2307   # focus one diagnostic code
python3 scripts/find_candidates.py --output --fresh     # JS/decl/sourcemap output diffs
python3 scripts/find_candidates.py --none --fresh --tsgo # hide tsgo-IRRELEVANT failures (see below)
```
**Skip-log filtering caveat (round 137):** `--fresh` extracts skip-set names as backticked
`name_ts` tokens — entries logged WITHOUT the `_ts` suffix (most of the round-133..136
one-liners) are NOT filtered, so previously-triaged tests keep appearing in the NONE
listing. The skip log lives in PLAN-PHASE-4-HISTORY.md since 2026-06-10 (the script reads
both files and unions the tokens); add new entries there, above the `### End of skip log`
terminator. Cross-check a candidate against both files
(`grep <name> PLAN-PHASE-4.md PLAN-PHASE-4-HISTORY.md`)
before re-investigating; suffix new entries with `_ts`.
The plain (no-flag) buckets only see tests that already emit some `error TSxxxx`
— ~33 of >1000 failures. **`--none` is where ~60% of the remaining work lives**
(see PLAN-PHASE-4.md § "STRATEGIC MAP"). Do not call the pool exhausted until
`--fresh`, `--none --fresh`, and `--output --fresh` are all dry.

**tsgo-relevance target (2026-06-05):** the compatibility target is the FUTURE
**tsgo** (TypeScript 7.0 / "Corsa"), NOT the legacy tsc 5.x corpus. Tests whose
whole point is a feature tsgo removed (legacy ES3/ES5 emit, AMD/System/UMD module
emit, removed options like `keyofStringsOnly`/`noStrictGenericChecks`/`charset`,
classic `node` resolution, JSDoc `@enum`/`@constructor`) are NOT worth chasing.
The policy + curated denylist live in **`TSGO-RELEVANCE.md`**; `scripts/tsgo_relevance.py`
classifies the current failures (RELEVANT / IRRELEVANT / DIVERGES) and the
`--tsgo` flag on `find_candidates.py` hides irrelevant ones. **Empirically (2026-06-05)
only ~6 of 808 failures are tsgo-irrelevant** — the bulk is tsgo-relevant core
type-checking, so the path to "finishing" is the type-engine Blockers, not
deprecated-feature pruning. When you investigate a failing test that targets a
removed feature, ADD it to TSGO-RELEVANCE.md's curated list (one-line reason)
instead of fixing it.

**Note:** All failures are deterministic (confirmed via 5-run study). Count variance between runs is caused entirely by dirty binary cache from interrupted runs, not JVM instability. **Gradle wipes XMLs when run with `--tests '*Name*'`** — the full suite must be re-run before `find_candidates.py` can report accurate results; the script warns if the XML count is below the expected ~27.

- **When hand-parsing JUnit XML to enumerate failing tests, use a real XML parser (`xml.etree.ElementTree`), NEVER a regex like `<testcase name="X"[^>]*>(.*?)</testcase>`.** JUnit emits PASSED testcases as self-closing `<testcase .../>` (no body) and FAILED ones with a `<failure>` child. A naive regex consumes a passed test's `/>`, then `(.*?)</testcase>` captures the NEXT (failing) testcase's body and ATTRIBUTES that failure to the passed test — silently shifting names and producing a garbage failing-list. This caused round-174's false "338/364 failures are order-dependent" conclusion (which mis-promoted B450); round-175 re-measured with `xml.etree` and found the 364 failures are GENUINE and DETERMINISTIC (running the failing-base patterns as an isolated batch reproduces all 364). The "Test ordering sensitivity" gotcha above is real but bounded (~25–50 boundary tests, both directions), not the bulk of the failing set.

## Anti-patterns to avoid

- Do not add content to this file that is already discoverable by reading the source or build scripts — that inflates context without adding signal, reducing AI agent task success rates (see [arxiv 2602.11988](https://arxiv.org/abs/2602.11988)).
- Do not use `grep` (without `-a` flag) on Gradle test output — it may contain binary content. Always use `grep -a`.
- **Do not re-analyze what to fix next.** PLAN-PHASE-4.md is already the prioritized plan. Pick the top unfinished item, implement it, done. Do not scan lists of failing tests or explore "low-hanging fruits" — that is wasted analysis time that could be implementation time.
