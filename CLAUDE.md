## Known gotchas

- **LOGICAL PARITY IS THE BAR, NOT BYTE PARITY (owner directive 2026-07-26; supersedes every "N corpus tests regress" veto in this file and the archive).** "The logical value of the compiler output at maximal performance should always be the deciding factor. Byte-by-byte parity is secondary if it can be achieved without extra cost." **So a corpus baseline that differs only in FORM — union member order, an equivalent message, a differently-shaped-but-equivalent elaboration — is no longer a blocker: write a NEW test case pinning the logic and switch the old one off** (say so in the session note, with the divergence and why it is logically equivalent). A baseline that differs in MEANING — a diagnostic that should fire and does not, a wrong type, wrong emitted semantics — is still a hard regression. This unblocks the general-engine work the byte gate priced out: many entries here and in the archive record a walker or rule as "DEAD — regressed N tests" **without checking whether those N were form or meaning**; such an entry is now a lead to re-examine, not a veto. **THE MECHANISM (round 717): a baseline is switched off ONLY by adding a `LogicalParityDivergence` to `logicalParityDivergences` in build.gradle.kts** — the generator then emits that subtest `@Ignore`d (so it stays VISIBLE as skipped, not vanished from the total), rewrites the ledger in `docs/logical-parity.md`, and FAILS the build on a stale entry or a `pinnedBy` class that does not exist under src/commonTest. Commenting an emission out, deleting a baseline, or widening a skip predicate to absorb a diff is NOT this mechanism. The form-vs-meaning decision tables (what counts as which, and the equivalence obligation per axis) are in `docs/logical-parity.md` § 2 — read them before classifying, and note that a form-only diff is a *candidate*, not an entitlement: byte parity is still preferred where it is free.
- **A RUNNING-SECTION PARTITION OF A *RECURSIVE* FUNCTION MUST HAND THE CALLER'S ROW BACK, NOT SKIP ON DEPTH (round 756, `CtaSections` level D).** The `if (depth != 1) return` shape used by levels A–C is only correct for a non-recursive function: applied to a recursive walker it charges the ENTIRE descent to whichever row was open at depth 1 (the dispatch row) and answers nothing. Instead `beginD()` closes the caller's running row and RETURNS it, `endD(prev)` closes its own and reopens `prev` — every row is then SELF time, exclusive of nested invocations, and the rows sum to the true total. Two consequences a reader must be told: the count column is boundary CLOSES (a row is also closed by every nested entry made while it is open), so per-invocation populations come from an arm census, never from that column; and the probe's activation window must be an explicit flag rather than `cur == <row>`, or the level dies under `COARSE` where the outer level's interior anchors do not fire — which is exactly what makes its own ON-vs-COARSE differential possible.
- **A DIFFERENTIAL CALIBRATION IS ONLY AS SHARP AS THE SMALLER OF ITS TWO SPREADS (round 756).** The sanctioned ON-vs-COARSE probe calibration FAILED on level D: Δ = 29 ms against a 26 ms within-mode spread, bounding the boundary at 31–168 ns and no better. Before quoting a differential, print both modes' run-to-run spread; if Δ is not several times the larger spread, say so and fall back to comparing both modes against the PROBE-FREE binary (which here gave 138 and 168 ns, and only the top of the range reconciled the partition with the independently measured total).
- **COST GATE (COST.1, round 717): anything that touches the checker runs `python3 scripts/cost_gate.py` alongside the suite.** It runs the compiler profile with `--passTiming`, extracts the DETERMINISTIC counters (getTypeOfExpression calls, narrowWalks, spineNodes, typeNode cacheable/bypassed, globals lookups) and diffs them against `docs/perf/cost-counters.txt`, failing above ±2%. Counters, never wall time — a loaded box swings ±13% and cannot see a 70 ms regression (round 713 added +11.5% getTypeOfExpression calls for one diagnostic and no gate noticed). An increase is not a veto but an accounting demand: justify it in the session note and `--update` the baseline in the SAME commit. Needs `build/bench/tsc-project-*` (create once with `scripts/bench-compile-tsc.sh --project compiler --no-emit --no-log`), and must NEVER run while `jvmTest` is in flight.
- **A RECORDED COUNTER BASELINE IS A CLAIM ABOUT A BUILD, NOT ABOUT A COMMIT — when the gate fails with no source change, REBUILD THE COMMIT THAT RECORDED THE BASELINE before believing either number (round 776).** Round 760's rebaseline recorded `typeNode.bypassed 104,162 -> 95,909`; its own commit, rebuilt, measures 104,162, and ablating the veto it credited moves the counter by ONE resolution — five later rounds re-measured against that unreproducible state and inherited it. A recorded delta is not evidence; a rebuild is.
- **PROGRAM ORDER IS THE CRAWL'S ORDER, AND `typeNode.bypassed` / `mapped.keyed` ARE A FUNCTION OF IT (round 776) — `ProjectCompiler.walk` SORTS, and removing the sort silently makes those two counters a property of the filesystem.** Which file first touches a shared type node decides whether INV.5(c) calls the resolution own-file or foreign: three orders of the same 78 files move them ~1% with the AST and every diagnostic bit-identical, so an order change looks exactly like a cost regression and shows up in NO output diff.


- **Do NOT poll for a Gradle run with a `while kill -0 $(pgrep -f "GradleWrapperMain.*jvmTest") ...; do sleep N; done` wait-loop — it never exits.** `pgrep -f` matches against the FULL command line, and the wait-loop's OWN command line literally contains the string `GradleWrapperMain.*jvmTest` (inside the pgrep pattern), so it matches ITSELF → `kill -0 <self-pid>` always succeeds → the loop sleeps forever, orphaned (harmless/idle, but never terminates and clutters the process list; clean up with `kill <pids>`). There is no need to poll at all: launch the suite with the Bash tool's `run_in_background: true` and react to the `<task-notification>` that fires when it completes (the harness re-invokes you). If you must poll for something, pick a pattern that cannot match the poller itself (e.g. a marker file's existence). Two long-lived JVMs (the Gradle daemon + `KotlinCompileDaemon`, ~hours uptime) are NORMAL idle build daemons — leave them; they speed up builds and auto-shut-down after their idle timeout. **The pkill variant is WORSE (round 466): `pkill -9 -f KotlinCompileDaemon` KILLS THE INVOKING SHELL ITSELF (the -f pattern matches the bash -c command line containing the literal), so everything after it in a compound command silently never runs — the tell is a Bash call that "completes" with no output and no side effects. Use a bracket pattern that cannot match itself: `pkill -9 -f 'KotlinCompile[D]aemon'`.**

### Measured dead-ends (full detail archived — do NOT re-attempt without reading the archive entry)


- **WHILE enum -> MEMBER IS DECIDED VACUOUSLY, NO TARGET CAN SEPARATE AN ENUM FROM A SUB-UNION OF ITS OWN MEMBERS — so ANY measurement of "does this enum narrow change a verdict" reads 0 by construction, not empirically (round 765, measured at the consumer).** A consumer-side differential over round 764's subtractive narrow found 4 relation consults on the compiler profile and 10 on services, **0 differing**, with EVERY consultation's target being the enum itself (`SyntaxKind` -> `SyntaxKind`, …) — a sub-union relates by union membership. Do NOT read such a zero as "the narrowing is dead weight, delete it": it becomes load-bearing the moment (REL.2)'s global rule lands. The falsification that makes a zero here trustworthy is to record a deliberately BOGUS baseline and confirm the counter reports differences; a perturbation that replaces the tracked VALUE instead destroys the tracking and can only ever report 0.
- **A CALL WHOSE CALLEE IS A MEMBER OF AN IMPORTED NAMESPACE IS NEVER ARGUMENT-CHECKED — `checkArgumentsAgainstSignature` does not run for it at all (round 766, isolated with three probes).** A same-file `namespace Debug` reaches the argument gate and a plain exported function imported from another file reaches it; an exported `namespace Debug` imported from another file does NOT, in both the direct-import and `export * from` barrel forms. That is **1,108 `Debug.<member>(…)` calls on the compiler profile and 1,518 on services** whose arguments no argument-position check ever sees. **So a call-argument fix that measures ZERO firings on the profiles is probably not inert — it is probably invisible**: price it against a probe that uses a plain imported function before concluding anything (rounds 764-766's arms all read 0 for this reason). It is NOT a general resolution failure — the flow-walk assert path resolves a namespace member fine.
- **A PER-KIND SPINE DISPATCH TABLE IS A CLOSED DIRECTION (round 732, measured and corpus-verified — `docs/perf/dispatch-table.md`): it removes 64% of the handler consultations and 4.8% of the time (883 ms upper bound of an 18.5 s spine; ~100-300 ms realistically).** The instrumentation (`SpineDispatch`, opt-in `--dispatchProbe`/`--dispatchGated`, behaviour-free when off) and the derived table STAY — re-derive from them, do not re-guess. **The law this adds to the caching one: a COUNT of avoidable work is not a MEASURE of it.** Round 716 sized this at 1.0-2.5 s from "IDENTIFIER is 44.5% of nodes at 2,746 ns and almost no handler wants an identifier"; in fact 22 of the 59 handlers ACT at an identifier, because the handlers keyed on PARENT edges, FRAME-owner identity (`frames.last().owner === node`) and nodeId REGISTRIES (`ctaM3NarrowThen`, `ccetRestores`, `cpaLoopVarRestores`) cannot be closed by the node's own kind AND are the expensive ones. **The spine's cost is SIX handlers holding 71% of it** — `cpaSpineLeave` 4,366 ms, `ccetSpineLeave` 3,046 ms, `spineCtaM3StatementAnchor` 2,900 ms, `spineIanyEnterNode` 1,025 ms, `ccetSpineEnter` 920 ms, `ctaSpineEnter` 586 ms, vs ~4.8 s for the other 53 COMBINED; that is cta/cpa/ccet legacy-parity frame bookkeeping, i.e. a per-handler problem (queue item (SPINE.1)). Two handlers LOOK own-kind-closed and are not: `spineArithLeaveNode` (a frame pop follows its `when (kindId)`) and `spineNpLeaveNode` (its `else` arm reaches every Expression kind) — never read only a handler's first three lines.
- **A SECTION-PROBE'S OWN BOUNDARY COST MUST BE PRICED DIFFERENTIALLY — an in-situ EMPTY-SPAN calibration over-reads by 3.5-4.4x and has now misled three consecutive rounds (733/734/735).** Back-to-back empty `at()` spans read 306 ns (unrolled) and 391 ns while the true cost is ~86-92 ns: a `repeat` loop puts a back-edge SAFEPOINT POLL inside every empty span, an unrolled sequence still attributes stop-the-world pauses, and a span across a non-inlinable call reads ~1 us (a cold transition, not a timestamp pair). **The only trustworthy figure is a DIFFERENTIAL: run the SAME code at N boundaries and at 1, divide by the extra boundary count.** `ArgSections` implements that as a MODE (`--argSectionsCoarse` keeps only the partition anchors, so a non-anchor boundary costs a static read and a not-taken branch); copy that shape rather than the empty-span loop. Per-section nanos are sound for RELATIVE attribution only, never as a production cost model.
- **When the thing being priced is SMALLER than a timestamp pair, AMPLIFY THE SIGNAL instead of shrinking the instrument (round 759, `docs/perf/claim-audit-round758.md` § 11).** A ~89 ns pair around a ~37 ns `globals[name]` probe would BE the measurement, and counters (round 736's escape) cannot price a `HashMap` get. `--globalsAmp r` brackets **r** reads of the same key under ONE pair, so `p(r) = cold + (r-1)*warm + boundary` and **two values of `r` cancel the boundary algebraically** — no calibration needed for the slope. Falsify it by ARITHMETIC, not timing: the sink must be an exact multiple of the hit count at every `r` (that is what rules out JIT elision), and the slopes from three independent pairs must agree. The in-situ empty bracket (`r < 0`) is used ONLY to split `cold` from the boundary, and its answer carries the 3.5-4.4x over-read caveat above.
- **THE FLOW-NARROWING TAIL IS EXTREME AND ITS THREE OBVIOUS CAUSES ARE ALL MEASURED FALSE (round 735, compiler profile): 394 of 70,037 walks (0.56%) cost 1,485 ms = 47% of all narrowing and 4.9% of the compile.** Before proposing anything there, know that the tail does NOT trip (`narrowWalk tripped: 0` — so the "tripped walks are never memoized, hence re-run in full" theory is dead), does NOT exhaust the 1,000,000-visit budget (630,641 arrivals across all 394; 1,601 each, max 19,515), and is NOT memoizable (`walkMiss cold=69,968` of 70,037 — essentially every launched walk is a first sighting, on top of the 40,709 the LIVE memo already serves). The residue is arithmetic: the tail runs at 2,354 ns per flow-node arrival against a 372 ns all-walk mean, i.e. 13x more arrivals AND 6.3x costlier arrivals. Diagnose with `--passTiming` (grep `narrowWalk`); full derivation in `docs/perf/argument-check-attribution.md`.

### Test assertion gotchas


- **An un-annotated PARAMETER is invisible to the body walkers no matter what its SIGNATURE says: they read `currentLocalTypes`, filled by `populateParameterLocalTypes`, whose first gate is `paramType != null` — writing `symbolTypes[param.id]` in `getTypeOfArrowFunction` (where `applyContextualParameterTypes` lives) has NO effect on TS2339/TS7006/etc. (round 694).** Contextual parameter typing that must reach the body — IIFE arguments, and any future source of parameter types — belongs in `populateParameterLocalTypes`. The probe that detects the mistake must FAIL if the change works (`((a) => a.nope)("x")` must become TS2339); a probe that merely watches the target case stay quiet cannot tell an inert change from a working one.
- **A `const k = <expr> as unknown as E` SUBJECT IS INVISIBLE AT THE ARGUMENT GATE — for a FILE-LEVEL enum too — so a narrowing pin written that way passes on a broken build for a reason unrelated to the fix (round 782, two pins).** Make the subject a PARAMETER (`function inner(k: E)`). General form: validate a probe SHAPE against a control whose answer is already known before using it to measure anything; a silence-asserting pin on an unobservable shape measures nothing.
- **A PRICE OR RESIDUAL MEASURED ON A SUBSET OF THE 8 PROFILES IS A CLAIM ABOUT THAT SUBSET ONLY (round 782).** Rounds 777-781 each quoted a scaffolded price as `compiler N -> M, services N -> M` and concluded "the residual is empty"; the 16th site lived in `src/harness` and was structurally invisible to all four. Run the full 8-profile grid before declaring a family closed — profile-unique files (harness/server/services) are exactly where a last straggler hides.
- **A NARROWING pin whose EXPECTED union happens to equal a type ALIAS declared in the same file reads the ALIAS NAME, not the members (round 764).** Unions are interned and carry `aliasDisplayMap`'s name, so with a `type U = K.A | K.B | K.C` in the prelude, `k !== K.D` reports `Argument of type 'U'` — the pin then measures the alias table instead of what it was written for. Choose a subtraction whose survivors match no declared alias (removing a MIDDLE member also tests member ORDER, which removing the last one cannot).
- **A NARROWING probe must assign to an INCOMPATIBLE type and read the narrowed type out of the error message — "no error here" cannot tell correct narrowing from a reference washed to `never` (round 760).** `never` is assignable to everything, so an over-narrowing is SILENT at every use except a call argument, and its symptom surfaces far away as the DECLARED type ("Argument of type 'Node' …"), which reads like no narrowing happened at all rather than too much. `const s: string = x` after the guard prints `Type 'Node'`/`Type 'Ident'`/nothing-at-all (= `never`) and discriminates all three in one run; the same trick reads any resolved member type (`const s: string = m.kind`).
- **WIPE THE WHOLE `build/test-results/jvmTest` DIR, NEVER JUST `/binary` — the documented incantation was changed to the whole dir; do not "restore" the `/binary` form (rounds 638 + 690).** `/binary` clears the binary results but NOT the per-class XMLs, so a script globbing `build/test-results/jvmTest/*.xml` sums the PREVIOUS run's files too. That is harmless only while the test SET is stable, and it lies silently the moment a change adds or removes tests — a removed test keeps "failing" from its stale XML, and a COUNT that should have moved and did not means the results dir, not the change. Worse for an AWAITED run (round 638): gradle deletes the stale XMLs only when the test task starts, i.e. after the multi-minute compile, so a count-based wait "succeeds" on stale results while the new suite is still compiling. The whole-dir wipe makes any XML seen later fresh by construction.
- **Hand-written test conventions (round-437 sweep, 2026-07-07) — new local tests MUST follow them**: compile via the shared `diagnose(source, directives = "// @strict: true", fileName = "t.ts")` helper (CompilerTestSupport.kt; trimIndents the source and prepends the directives line) — never a per-file `TypeScriptCompiler().compile(...)` helper (EXCEPTION: a test asserting SYMBOL IDENTITY may construct `Checker(options, binderResults)` directly — cf. Inv3PerFileLookupTest — but its fixture fileNames MUST be path-shaped (`/proj/c.ts`): flat corpus-style names silently defeat directory-relative module-specifier resolution, so every import resolves null); assert via the `should`/`have` idiom (`diagnose(...) should { have(none/any { it.code == NNNN }) }`, com.xemantic.kotlin.test) or power-assert `assert(actual == expected)` — never `assertEquals`/`assertTrue(d.isEmpty(), msg)` (round 682 converted 792 `assertEquals` call sites; `assert` and `have` are the ONLY power-assert-transformed functions per build.gradle.kts, and they take NO message — the diagram renders every subexpression value, which beats any hand-written one). TWO traps when writing `assert(a == b)`: an empty-collection comparison must be `assert(xs.isEmpty())`, since `== emptyList()` gives the compiler no way to infer the element type; and an AST-valued subexpression must stay on `assertEquals` (next entry); sources are multiline templates (not buildString), class-shared TS preludes are a trimIndented `private val` concatenated by the caller (`diagnose(prelude + """…""")`), test names are backtick sentences (dots replaced — see the Kotlin backtick-name rule above; use `negative control - …` phrasing for negative tests).
- **Never put an AST node / node list / SourceFile subexpression inside a power-assert-transformed assertion (`have`/`assert` from com.xemantic.kotlin.test)** — on failure the diagram toStrings every captured subexpression, which for a data-class node dumps (or, on deep chains, STACK-OVERFLOWS rendering) whole subtrees, masking the real failure as SOE/OOM. Compute ints/booleans into locals first, or use plain `kotlin.test.fail` with a hand-built message (cf. ForEachChildOracleTest). This is why the round-682 `assertEquals` sweep DELIBERATELY left 27 sites on `assertEquals` — every site in Inv2NodeIndexTest / Inv2LexicalScopeTest / ForEachChildOracleTest whose compared value is a node, a `.copy()`, a `preorder(...)` element or a lexical scope. A `List<Diagnostic>` or a `CompilationResult` is SAFE to render (strings + diagnostics, no AST); a `SourceFile`/`NodeBase`/`Symbol`/lexical scope is not. **This is the ONLY sanctioned exception to the one-idiom rule above** — the 65 surviving `kotlin.test` calls are ALL in the six AST-centric files (Inv2LexicalScopeTest, Inv2NodeIndexTest, Inv3NodeKeyedLookupTest, Inv3PerFileLookupTest, RealLibSnapshotTest, ForEachChildOracleTest); a `grep assertEquals src/` hit outside those files is drift to convert, not precedent to copy.
- **ONE assertion idiom in tests: power-assert `assert(<boolean expr>)` (com.xemantic.kotlin.test) — do NOT reintroduce `kotlin.test.assertEquals`/`assertTrue`/`assertFalse`/`assertNull`/`assertNotNull`/`assertSame`/`assertContains` (round 682 converted 1,009 call sites; only `assert` and `have` are power-assert-transformed per build.gradle.kts `powerAssert.functions`).** They take NO message — the diagram renders every subexpression value, which strictly beats a hand-written one (a broken pin prints the operand value, the `false` verdict AND the receiver's contents). Translations: `assertEquals(exp, act)` → `assert(act == exp)` (ACTUAL first); `assertTrue(c)` → `assert(c)`; `assertFalse(c)` → `assert(!c)` (parenthesise if `c` has a top-level operator, else `!` mis-binds); `assertNull(x)` → `assert(x == null)`; `assertSame(exp, act)` → `assert(act === exp)`; `assertContains(coll, e)` → `assert(e in coll)`; `assertNotNull(x)` → `assert(x != null)` — and in VALUE position (`val v = assertNotNull(expr)`) split into `val v = expr` + `assert(v != null)`: `assert` carries `contract { returns() implies actual }`, so `v` SMART-CASTS to non-null afterwards (no `!!` needed). FOUR traps: an empty-collection compare must be `assert(xs.isEmpty())` (`== emptyList()` gives the compiler no element type to infer); `kotlin.assert` is a different function (see the Kotlin/Native entry above); an AST-valued subexpression must stay on `assertEquals`/`assertNotNull` (next entry); and **a SCRIPTED conversion may re-flow the argument EXPRESSIONS but must NEVER re-flow their string literals** (round 684: whitespace-normalising every rewritten argument collapsed the needle `"…\n    // second comment line"` — whose four spaces ARE the emit indentation the pin exists to check — into one space). Audit any scripted sweep by diffing the multiset of string literals before/after and accounting for EVERY disappearance; the only expected ones are the dropped messages.
- Avoid partial `assert("x" in result)` — always assert the full expected output.
- **A NARROWING pin that asserts a TS2339 APPEARS discriminates NOTHING — it passes on a working AND a broken build, for opposite reasons (round 751).** `case K.Alpha: return x.b` errors both when narrowing correctly REMOVED `B` (missing on `A`) and when narrowing never ran at all (missing on `A | B`); two such pins passed on the pristine build they were written to fail on. Assert the NEGATIVE branch instead — `default: return x.b` with `none { it.code == 2339 }` — which only a build that actually subtracted the constituent can satisfy. Same rule for any "the filter removed something" pin: assert what becomes LEGAL, not what stays broken.
- **A memo whose decision reads MUTABLE state cannot be validated by inspecting its answers — a frozen-wrong entry looks exactly like a correct one (round 751).** `canonicalEnumSymbol` freezes per `sym.id` a verdict depending on `globals[name]`/`enumValues[global.id]`, and a first touch before the enum's values exist returns `sym` itself — i.e. reports `canonical(sym) === sym`, which is indistinguishable from a genuinely-canonical symbol, so round 750's "153 canonical, 0 redirected" was ALSO what a fully-frozen cache would print. The only probe that can see it recomputes the decision with the memo BYPASSED and diffs against the memoized answer (measured 0 divergences round 751). Applies to any order-dependent memo in the checker, not just this one.
- **DO NOT PIN A KNOWN-OPEN GAP AS A "control" — it is a countdown, not a guard (round 765, one suite failure).** Round 764 pinned "a switch `default:` still answers the whole enum" so the gap would read as measured; round 765 closed the gap and the pin failed by construction. Record an open gap in the SESSION NOTE instead. The corollary for the closing round: **the filtered batch must include the test class of every previous round whose session note named the shape you are fixing** — a batch of corpus letters plus your own new class will not catch it, because the stale pin is in neither.
- **Test ordering sensitivity**: Adding new checker code that increases diagnostics can cause deterministic failures in unrelated JS emit tests — tests pass individually but fail in the full suite. Always run the full suite to verify no regressions.

### Kotlin idioms


- **NEVER key a HashMap/HashSet by an AST NODE with a large subtree (FunctionDeclaration, class/namespace bodies) — AST nodes are Kotlin data classes, so `hashCode()`/`equals()` DEEP-recurse the whole subtree on every lookup** (round 471: a `HashMap<FunctionDeclaration, String>` in buildNestedFunctionMap cost the services self-compile +10 s, 39 → 51 s; replaced by cluster-order-aligned file lists). The existing `builtinLibDecls`/`builtinLibMemberDecls` node-sets survive because lib decl subtrees are small — not a licence. Key by `Symbol.id`/`Type.id`/pos-based keys, or keep parallel lists aligned to an existing order.

- **Kotlin's `mutableMapOf()`/`mutableSetOf()` return LinkedHashMap/LinkedHashSet — ordered, so they pay `LinkedHashMap.afterNodeInsertion` on every put and an ordered copy on construction (round 483: ~5% of the compiler self-compile self-time was `afterNodeInsertion`).** On a HOT, order-INDEPENDENT map/set — especially one COPIED per scope entry — write `HashMap()`/`HashSet()` (and `HashMap(other)`/`HashSet(other)` for copies, NOT `.toMutableMap()`/`.toMutableSet()`, which always return the linked variant). The per-function-body scope structures (`currentLocalTypes`, `currentLocalDeclTypeNodes`, `currentShadowedNames`, `currentParamBindingNames`) and `getUnionType`'s dedup set are HashMap/HashSet for exactly this reason. **Before converting, PROVE order is unused**: grep the field for `.keys/.values/.entries/.forEach/.map/.iterator/.first/.joinToString/.sorted` — a map whose iteration feeds DISPLAY or DIAGNOSTIC output (member order, union display) MUST stay ordered, so this is a per-field audit, not a blanket sweep.
- **The build is WARNING-CLEAN (0 compiler warnings; the 2026-07-04 sweep cleared 1,025) — KEEP IT THAT WAY: fix every new compiler `w:` the moment it appears, never let them accumulate.** `extraWarnings = true` + `progressiveMode = true` (build.gradle.kts) mean some warnings become HARD ERRORS on a Kotlin bump (any "will become an error in language version 2.4" note), and a warning routinely flags a REAL BUG — the sweep found `minArgumentCount` was always 0 because `it.questionToken == null` compares a `Boolean` (never null). Check with `./gradlew compileKotlinJvm compileTestKotlinJvm --rerun-tasks 2>&1 | grep -a '^w:'` (needs `--rerun-tasks`; Gradle caches by content hash and does NOT re-emit warnings on an up-to-date compile). Every fix must be behavior-preserving — gate on the full corpus suite; `USELESS_CAST`/redundant-`!!`/redundant-`?.` are identical static types (safe), but "always true/false" and unused-var removals can drop a load-bearing smart-cast or side effect (a bare `x as T` statement smart-casts `x`), so compile + suite after each batch.
- **`*/` inside KDoc terminates the comment**: A `/** ... */` doc comment ends at the first `*/`. Embedding `*/` (e.g. when documenting a JSDoc pattern) silently breaks the rest of the declaration — a data-class body following a broken doc comment surfaces as a cascade of confusing errors like "Modifier 'override' is not applicable to 'local variable'", "No parameter with name 'pos' found", "Unresolved reference 'jsDocTagEnd'". Reword to "comment-close" or escape as `*\/`.
- **Kotlin block comments NEST — a literal `/**` *inside* a KDoc opens a nested comment level (B151)**: writing the JSDoc string `/** @overload ... */` inside a `/** ... */` doc comment makes the inner `/**` open a NESTED block comment, so the doc comment's closing `*/` only drops back to depth 1 and the comment runs to EOF → `Syntax error: Unclosed comment` at the last line + a cascade of "Unresolved reference" errors for class members BEFORE the doc comment (the whole class fails to parse). This is DISTINCT from the `*/`-closes-early gotcha above: here it's the `/**` opener that bites. When documenting JSDoc tag syntax in a KDoc, never write a literal `/**` (or `/*`) — describe it as "a JSDoc comment" or use single-line `//` comments. **WORSE, SILENT variant (round 390, build.gradle.kts): a path GLOB in a KDoc (e.g. writing src-slash-lib-slash-star-dot-d-dot-ts) also contains the nested-comment opener — and when a LATER declaration's `*/` happens to re-balance the depth, the file COMPILES with a silently-DEAD region: tasks/vals declared inside it simply don't exist ("Task not found", top-level statements never run), and even a syntax error appended inside the swallowed span "builds successfully". If a build-script region mysteriously does not execute, scan comment-nesting depth before anything else.**
- **No non-stdlib dependencies in `commonMain`**: The project targets Kotlin Native (in addition to JVM/JS), so `commonMain` must use only `kotlin.*` and `kotlinx.*` packages. No `java.*`, no `BigDecimal`, no JVM-only types. Use Kotlin's built-in numeric types and stdlib math (`kotlin.math.*`).
- **Enum context resolution** (Kotlin 2.1+): When the expected type is an enum, use unqualified entry names — write `Equals`, not `SyntaxKind.Equals`. This applies to `when` branch conditions, named arguments (`operator = Equals`), comparisons (`flags == VarKeyword`), and any other position where the enum type is inferred. Caveat: if a data class has the same name as an enum entry (e.g. `LabeledStatement`), keep the `SyntaxKind.` prefix to avoid ambiguity.
- **No JVM-only APIs in `commonMain`**: `Map.putIfAbsent` → use `getOrPut`; `Math.pow` → use `kotlin.math.pow` extension; `RegexOption.DOT_MATCHES_ALL` → use `[\s\S]` in the pattern (B259). `./gradlew compileKotlinJvm` does NOT catch these — it compiles only the JVM target. Always use Kotlin stdlib equivalents for multiplatform compatibility.

Check off the item (`- [x]`), **bump STATUS.md** (corpus count if it moved, dashboard metrics if the item moved them), add a session note to PLAN-PHASE-5.md (under the live notes heading, most recent on top), add a CLAUDE.md gotcha if applicable, **commit and push** (one commit per sub-step — keeps history bisectable and lets the next agent pick up mid-stream without re-running everything). STATUS.md drift is a real failure mode — past sessions committed `(+N)` work without bumping the count, so the next agent saw a stale baseline. **Trim-on-write (the anti-balloon rule)**: when bumping STATUS.md, keep only the ~5 most-recent round notes — move older ones to docs/history/STATUS-HISTORY.md in the same commit; when adding a session note to PLAN-PHASE-5.md, if more than ~10 rounds are live, move the oldest to docs/history/PLAN-PHASE-5-HISTORY.md in the same commit. Both files ballooned (160 KB / 1.7 MB) before the 2026-06-10 trim because sessions appended without trimming.
6. **Loop back to step 1** and pick up the next item. Keep going until one of these stop conditions:
   - Context budget is running out — finish the current item cleanly, commit, then stop.
   - Every remaining queue item is gated on user-policy decisions (Guardrails) AND no in-scope unblocker work remains. This should be rare — under the promote-unblocker default, blockers turn into queue items, so the queue rarely runs dry.
7. End the session with a concise summary of items completed, unblockers promoted (with what they unblock), items left pending user decisions, and net test count delta.

**Autonomous-decision policy (when an item appears blocked):**

When an item can't be implemented surgically — e.g. the diagnostic relies on infrastructure that doesn't exist yet (super-keyword resolution, full flow-graph, generic argument inference) — **promote the unblocker, do not skip the item**:

- **Promote-unblocker (default)**: identify the smallest concrete infrastructure piece that would unblock the item, insert it at the TOP of the queue with a one-line description and a back-pointer to the original item (and any other items it would also unblock — list them). Then start work on the unblocker. The original item stays unchecked; it gets picked up automatically on a future loop. Cross-phase work (binder + checker together, scope-chain restructuring, new cache layers) is in scope — that is exactly the work this policy exists to drive.
- **Decompose first if large**: if the unblocker is itself a multi-step change, split it into the smallest standalone sub-step that lands as a single commit without regressions, queue that, and only that. Do not attempt the whole infrastructure piece in one pass. Subsequent sub-steps get queued as separate items as the work progresses.
- **Time budget per attempt**: cap each attempt at one full-suite verification cycle. If it regresses, revert. After revert, you may either (a) try a different decomposition for the same unblocker, or (b) move to the next queue item — but record both attempts in the session note. Do not iterate more than twice in one session on the same regressing approach; if neither works, write up what you learned (which paths broke, what the underlying coupling is) and queue a follow-up "investigate X" item.
- **Skip is reserved for Guardrails only**: the only legitimate skip is when the unblocker requires a user-level decision listed under Guardrails below. For those, leave a `BLOCKED-PENDING-USER:` marker on the item with a one-paragraph proposal for the user to react to, then continue with the next queue item. Do NOT end the session.
- **No silent abandonment**: every promote/decompose/skip writes a session note (docs/history/PLAN-PHASE-4.md, most recent on top) with root cause, what was attempted, and what landed. Never leave an item half-done in the working tree.

**Anti-loop rule — recon-only sessions are a protocol failure:** ending a session with no code landed, on the grounds that recon found nothing, is NOT a legitimate outcome while the queue holds unchecked items. In Phase 17 the live pool is the PLAN-PHASE-5.md QUEUE plus any dashboard regression, so "the pool is dry" is never true while unchecked queue items remain; recon is part of step 1, never the deliverable. The full protocol — the `0/0/0` false-exhaustion mechanism, the three-bucket dryness rule, the mis-structured-queue diagnostic, and the forbidden session-end commit patterns — is in the **`corpus-triage` skill**; load it if you are about to end a session without landing code, or when triaging a corpus regression.

**Guardrails requiring user input** (do NOT decide autonomously):
- Build system changes (Gradle config, dependency add/remove/upgrade, Kotlin version bump).
- Test-generation pipeline changes (`generateTypeScriptTests`, baseline format, skipped-tests log structure).
- Re-enabling currently-disabled test categories (e.g. `.errors.txt` → +9k tests).
- EXCEPTIONS pre-approved 2026-07-02 (see PLAN-PHASE-5.md § Approvals): conformance-category adoption in the generator (M3.0), the real-lib migration (M2), and the M5 native-target re-enable.

**Other rules:**
- **Do NOT switch items** mid-task — finish the current item (commit + push) before starting the next.
- **Commit between items** — never bundle two unrelated sub-steps into one commit. Each committed sub-step leaves the repo in a clean state for the next agent.
- **Analysis items** (item 0) should produce written artifacts (design docs, categorized lists) before any code is written.
- **No regressions** — the currently passing tests must continue to pass after every change. Re-run the full suite between sub-steps; a +1 / -2 swap is still a regression.
- **Full-suite run caveat**: a clean JVM test run takes ~4-6 minutes. Budget accordingly when deciding whether to attempt another item.

## How to run tests


```bash
# Full suite (wipe the WHOLE results dir first — not just /binary; stale XMLs inflate
# the count and survive a /binary-only wipe, see the round-638/690 gotcha above):
rm -rf build/test-results/jvmTest && ./gradlew jvmTest 2>&1 | grep -a "tests completed"

# Single test (get expected vs actual diff):
rm -rf build/test-results/jvmTest && ./gradlew jvmTest --tests '*.<TestName>*' 2>&1 | grep -a -A 40 "message" | head -50
```

**Corpus-regression triage** — the `find_candidates.py` buckets and flags, the skip-log
filtering caveat, the pin-position rules, and the tsgo-relevance policy live in the
**`corpus-triage` skill** (CORPUS-era machinery; load it when diagnosing a corpus-test
regression). Two facts that stay resident because they bite outside triage: all failures
are DETERMINISTIC (run-to-run count variance is a dirty binary cache, never JVM
instability), and **Gradle wipes the XMLs when run with `--tests '*Name*'`** — so the full
suite must be re-run before any XML-reading script can report accurate results.

- **When hand-parsing JUnit XML to enumerate failing tests, use a real XML parser (`xml.etree.ElementTree`), NEVER a regex like `<testcase name="X"[^>]*>(.*?)</testcase>`.** JUnit emits PASSED testcases as self-closing `<testcase .../>` (no body) and FAILED ones with a `<failure>` child. A naive regex consumes a passed test's `/>`, then `(.*?)</testcase>` captures the NEXT (failing) testcase's body and ATTRIBUTES that failure to the passed test — silently shifting names and producing a garbage failing-list. This caused round-174's false "338/364 failures are order-dependent" conclusion (which mis-promoted B450); round-175 re-measured with `xml.etree` and found the 364 failures are GENUINE and DETERMINISTIC (running the failing-base patterns as an isolated batch reproduces all 364). The "Test ordering sensitivity" gotcha above is real but bounded (~25–50 boundary tests, both directions), not the bulk of the failing set.

## Anti-patterns to avoid


- Do not add content to this file that is already discoverable by reading the source or build scripts — that inflates context without adding signal, reducing AI agent task success rates (see [arxiv 2602.11988](https://arxiv.org/abs/2602.11988)).
- Do not use `grep` (without `-a` flag) on Gradle test output — it may contain binary content. Always use `grep -a`. **SOURCE greps too: `Checker.kt` itself trips grep's binary heuristic (control bytes in string literals), so a plain `grep pattern src/.../Checker.kt` silently returns NOTHING for text that IS there** — round 500 nearly re-derived `perFileScope` from scratch this way, and an earlier session wrote a stale "never consumed" queue claim the same way. Retry any surprising empty grep over `src/` with `-a` before concluding code is absent.
- **Do not re-analyze what to fix next.** docs/history/PLAN-PHASE-4.md is already the prioritized plan. Pick the top unfinished item, implement it, done. Do not scan lists of failing tests or explore "low-hanging fruits" — that is wasted analysis time that could be implementation time.
